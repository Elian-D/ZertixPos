# ZertixPOS v1.3.0 — Multi-tenant (SaaS)

**Fecha:** 2026-08-26
**Contexto:** `docs/features/roadmap-v1.2-v1.5.md` fijaba v1.3.0 en Multi-tenant vía `stancl/tenancy` (adelantada desde v1.5.0 original). Este documento reemplaza el resumen del roadmap para v1.3.0 con el desglose real, fase por fase — construido a partir de `docs/features/v1.3.0-checklist.md` (el borrador de comparación, ya cerrado) una vez que todo el alcance quedó confirmado contra documentación real de los paquetes involucrados (`stancl/tenancy`, `spatie/laravel-permission`, `srmklive/laravel-paypal`) y contra el código real del proyecto, no solo el plan original del roadmap.

**Disciplina de espejo:** igual que `v1.1.0.md`/`v1.2.0.md`, la Tabla de Requerimientos de abajo es un espejo exacto del desglose por Fase — un REQ, una sección, mismo número. La tabla es solo el resumen para ubicar rápido qué es cada cosa; el detalle real (el porqué, las correcciones encontradas al ejecutar, verificaciones) vive en el desglose, no en la tabla.

**Orden por dependencia, no por orden del roadmap original.** El roadmap listaba 6 bloques sin jerarquía entre sí; acá se ordenan de lo que todo lo demás necesita primero, a lo que menos depende de otras piezas:
0. **Migración de DataTables a Livewire (`Opción C`, decisión 2026-08-26)** — no estaba en el roadmap original. Se adelanta a Fase 0, antes de todo lo demás, porque el Panel de Súper Admin (Fase 5) y cualquier vista nueva de Multi-tenant nace directo en este motor — construirlas primero en el motor AJAX viejo significaría migrarlas después de todos modos. Sin producción desplegada todavía (confirmado, ver Fase 2), no hay riesgo de regresión sobre clientes reales al migrar las 24 tablas existentes de una vez, a diferencia de lo que habría aplicado si ya hubiera clientes en producción.
1. **Separación landlord/tenant** — nada del resto existe sin esto (ni tabla `tenants`, ni conexión landlord, ni guard de staff).
2. **Roles y Permisos** — no depende técnicamente de 1, pero se hace ahora para que el módulo del Wizard/Súper Admin (Fases 4-5) agregue sus permisos nuevos ya sobre la convención correcta, en vez de mezclar dos convenciones y tener que renombrar dos veces.
3. **Modelo de suscripción, pasarela de pago y middleware de corte** — depende de que exista `tenants` (Fase 1). Es la base de datos que tanto el Wizard (la crea) como el Súper Admin (la lee) van a necesitar.
4. **Wizard de aprovisionamiento** — depende de 1 (Tenant/Domain) y de 3 (no puede cobrar ni crear una suscripción si el modelo no existe todavía).
5. **Panel de Súper Admin** — depende de 1 (guard landlord), de 3 (qué mostrar) y de 0 (nace directo en el motor Livewire nuevo); es la superficie de gestión de lo que 3 y 4 producen, tiene sentido cerrarla después de que haya algo real que gestionar.
6. **DNS comodín** — la pieza menos dependiente de todas; es configuración de infraestructura (Cloudflare) sin código real detrás, salvo una validación chica que vive dentro de la Fase 4. Podría hacerse en paralelo desde el día uno sin bloquear nada.
7. **Catálogo de NCF sin CRUD + Centro de Configuración (agregada 2026-08-27)** — depende de 0 (usa el motor Livewire nuevo, migra `NcfType` directo a su forma final en vez de dos veces). No depende de landlord/tenant en sí, pero va después porque el hub de configuración necesita que las páginas que enlaza (Usuarios, Roles, Módulos) ya existan en su forma real.

**Estrategia de ramas — mismo patrón que v1.2.0, con rama padre real:**

- **`release/v1.3.0`**, creada desde `dev`.
- Cada `feature/v1.3.0-*` de las fases de abajo se rama **desde `release/v1.3.0`** (no desde `dev`), y su PR apunta **de vuelta a `release/v1.3.0`** — no a `dev`.
- Las 4 sub-fases de Fase 0 (0.7-0.10) nacen de `feature/v1.3.0-datatable-base` **ya mergeada** a `release/v1.3.0`, no en paralelo con ella — necesitan el motor listo primero.
- Al cerrar todas las fases, un único PR final mergea `release/v1.3.0` → `dev`.

```
release/v1.3.0
├─ feature/v1.3.0-datatable-base          (Fase 0 — el motor, ningún módulo todavía)
├─ feature/v1.3.0-datatable-crm-ventas    (Fase 0.7 — Clientes, Ventas, Cotizaciones)
├─ feature/v1.3.0-datatable-inventario    (Fase 0.8 — Productos, Almacenes, Movimientos)
├─ feature/v1.3.0-datatable-finanzas      (Fase 0.9 — Cuentas, CxC, Cobros — sin NCF)
├─ feature/v1.3.0-datatable-sistema       (Fase 0.10 — Usuarios, Roles — absorbe REQ-2.8)
├─ feature/v1.3.0-landlord-foundation     (Fase 1)
├─ feature/v1.3.0-permissions-rename      (Fase 2)
├─ feature/v1.3.0-subscriptions           (Fase 3)
├─ feature/v1.3.0-install-wizard          (Fase 4)
├─ feature/v1.3.0-super-admin             (Fase 5)
└─ feature/v1.3.0-config-hub              (Fase 7 — catálogo NCF + Centro de Configuración)
```

**Fase 6 (DNS) no tiene rama de código propia** — es configuración de infraestructura pura en Cloudflare, sin repositorio de por medio. La única pieza de código real de esa fase (validar subdominios reservados) vive dentro de `feature/v1.3.0-install-wizard` (Fase 4), donde está el campo de subdominio del wizard.

## Fase 0 — Migración de DataTables a Livewire (REQ-0)
**Rama base:** `feature/v1.3.0-datatable-base` · **Sub-fases:** `feature/v1.3.0-datatable-{crm-ventas,inventario,finanzas,sistema}`

### Por qué esta fase existe y por qué va primero

**Decisión del usuario (2026-08-26), no estaba en el roadmap ni en el plan original de v1.3.0.** El análisis previo (comparando 3 opciones: closures sobre el AJAX actual, instalar `orvian/kit` como paquete Composer, o portar el patrón sin el paquete) había recomendado construir la base Livewire como tarea aislada y usarla **solo** para pantallas nuevas (el Panel de Súper Admin), dejando las 24 tablas existentes en AJAX hasta que se tocaran por otra razón — la razón para no migrar todo de una era el riesgo de regresión sobre clientes reales en producción.

**Esa razón ya no aplica: confirmado que no hay producción desplegada, ningún cliente real todavía.** Sin ese riesgo, migrar las 24 tablas de una vez antes de lanzar evita el escenario contrario — salir a vender con la mitad del sistema en un paradigma (AJAX vainilla) y la mitad en otro (Livewire), exactamente la inconsistencia dual que `docs/promts.md` ya señalaba como problema sin fecha de resolución. Por eso se adelanta a Fase 0, antes incluso de la separación landlord/tenant.

**Opción elegida: "Opción C" — portar el patrón, no instalar `orvian/kit` como paquete.** Se descartó instalarlo como dependencia Composer externa (symlinks, dos historiales git, `vendor:publish`, paleta ajena que hay que reescribir de todos modos) — ese costo solo se paga si existe un segundo producto consumidor, que hoy no existe. El código vive directo en `app/` de ZertixPOS, con los namespaces y tokens reales del proyecto.

**Cifra final distinta a la estimación original de "24 tablas" (2026-08-27):** el número real fue 22 módulos migrados (CRM 6 + Ventas 3 + Inventario 6 + Finanzas 5 + Sistema 2), tras corregir el alcance de cada sub-fase contra el sidebar real (0.7-0.10) y sacar explícitamente `NcfType` (Fase 7, forma final distinta), Asientos Contables/Plan de Cuentas (`accounting.advanced`, fuera de alcance por decisión de producto) y Tipos de Pago/Documento (ya migrados a cards, nunca fueron tablas AJAX que migrar).

### 0.1 — El motor base (REQ-0.1)

Porte de `Orvian\Kit\Livewire\Base\DataTable` a `App\Livewire\Base\DataTable` — mismo diseño (`columns()`/`filterMap()`/`filterOptions()` como los 3 métodos que el hijo implementa, `getActiveChips()`/`toggleColumn()`/`clearFilter()` heredados sin reescribir), namespace del proyecto. Los ~8 componentes Blade de soporte (`data-table/cell`, `column-selector`, `filter-chips`, `filter-container`, `filter-date-range`, `filter-group`, `filter-range`, `filter-select`, `filter-toggle`, `per-page-selector`, `search`, `skeleton`, `empty-state`, 3 vistas de paginación) se portan tal cual en estructura, solo cambia lo de REQ-0.2.

### 0.2 — Repintado de tokens (REQ-0.2)

Revisado componente por componente contra `tailwind.config.js` real: `orvian-orange`/`orvian-navy`/`dark-card`/`dark-border`/`dark-bg` no existen en ZertixPOS — si se copiara el kit tal cual, cada botón/select/chip/paginación de la suite renderiza sin color, en silencio (Tailwind no genera utilidades para clases que no están en su config, no hay error, solo se ve roto).

- `orvian-orange` → `zertix-primary`
- `orvian-navy` → `zertix-secondary`
- Cualquier clase `dark:*` → **eliminada, no reemplazada.** `CLAUDE.md` es explícito: el dark mode está preparado (tokens `.dark` reservados) pero no construido — inventar valores para clases `dark:` ahora sería adivinar una paleta que todavía no existe, y quedaría desactualizada el día que el dark mode real se construya.

### 0.3 — `FilterInterface` evolucionado (REQ-0.3)

**El contrato real no calzaba tal cual, y se resuelve ahora porque de todos modos se tocan los 118 archivos.** `App\Filters\Contracts\FilterInterface::apply(Builder $query): Builder` (ZertixPOS) construye cada filtro con un `Request` y lo lee internamente (`ProductsCategoryFilter`, patrón real). `Orvian\Kit\Filters\Contracts\FilterInterface::apply(Builder $query, mixed $value): Builder` recibe el valor inyectado, sin `Request` — porque Livewire no tiene un `Request` por filtro, los valores viven en la propiedad pública `$filters` del componente.

Se evoluciona la interfaz existente (no se crea una paralela — nada fuera de estas 118 clases depende de la firma vieja):
```php
// Antes
interface FilterInterface { public function apply(Builder $query): Builder; }

// Después
interface FilterInterface { public function apply(Builder $query, mixed $value): Builder; }
```

### 0.4 — Colapso de filtros simples (REQ-0.4)

### 1.1 — Instalar el paquete (REQ-1.1)

**Primer paso real, literal, antes de tocar cualquier modelo o tabla a mano:**
```bash
composer require stancl/tenancy
php artisan tenancy:install
```
`tenancy:install` scaffoldea todo lo que la Fase 1 necesita de base — no se construye nada de esto desde cero:
- `app/Providers/TenancyServiceProvider.php` (listeners de eventos, registro de rutas de tenant)
- `config/tenancy.php` (donde se configura `central_domains` — la lista de dominios que NO son de ningún tenant, ej. el propio `zertixpos.com` sin subdominio, o `localhost` en dev)
- `routes/tenant.php`
- Las migraciones `create_tenants_table.php` y `create_domains_table.php`

Falta un paso manual que la doc marca explícito: registrar `TenancyServiceProvider::class` en `bootstrap/providers.php`, justo debajo de `AppServiceProvider`.

**"Landlord" no es una tercera base de datos.** Confirmado contra la documentación oficial de `stancl/tenancy` ("The two applications"): la conexión central es la conexión por defecto de siempre — la misma MySQL que ya está en producción — sin migrar nada. Lo que el paquete agrega es una conexión de **tenant**, que se activa/desactiva según el subdominio de cada request. Cada cliente nuevo de aquí en adelante obtiene su propia base física; el landlord es la de siempre, repurpuesta para alojar `tenants`, `domains`, y los usuarios de staff (REQ-1.3).

`domains` es una tabla separada de `tenants` (relación `hasMany` vía el trait `HasDomains`) — no una columna `subdomain` suelta — porque un tenant puede tener más de un dominio apuntando a él (ej. dominio propio de un cliente grande a futuro, sin rediseñar el esquema cuando llegue ese caso).

**Mover las rutas existentes a contexto tenant — paso que faltaba explícito (2026-08-27).** Confirmado contra la doc real: `routes/web.php` (y por extensión todo `routes/app/*.php`, incluido desde ahí) es **central por defecto** — `tenancy:install` no lo toca. Como todo lo que hoy existe (POS, ventas, inventario, clientes, todo) es el negocio real del cliente, tiene que vivir en contexto **tenant**, no central — se mueven/incluyen dentro del grupo de `routes/tenant.php` (el que ya trae el middleware de inicialización de tenancy). Si se dejan en `web.php` tal cual, van a responder siempre en el dominio central, nunca dentro de la base de un tenant.

**Consecuencia práctica para seguir probando en local:** como esas rutas ahora solo responden en contexto tenant, hace falta un tenant de desarrollo sembrado a mano:
```php
$tenant = App\Models\Tenant::create(['id' => 'dev']);
$tenant->domains()->create(['domain' => 'dev.localhost']);
```
El propio `TenancyServiceProvider` migra/siembra automáticamente al crear el tenant (evento `TenantCreated`). Se entra por `dev.localhost:8082` (puerto real de Sail en este entorno — `APP_PORT` en `.env`, no el `8000` de `php artisan serve`; `*.localhost` ya resuelve solo a `127.0.0.1`, ver REQ-6.2). `localhost` a secas (o lo que se configure en `central_domains`) queda para el landlord — vacío hasta que Fases 4/5 construyan algo ahí.

### 1.3 — Guard `landlord` (REQ-1.3)

**Confirmado: reusa `spatie/laravel-permission` tal cual — no requiere paquete nuevo ni RBAC propio.** Modelo `App\Models\Landlord\Admin` (`app/Models/Landlord/Admin.php`), Eloquent normal en la conexión por defecto (central), con `HasRoles`. Guard `landlord` + provider `admins` en `config/auth.php`. Migraciones de Spatie **propias del landlord** (`roles`/`permissions`/`model_has_roles`, migración separada de la de negocio — ver REQ-1.7) corridas con `migrate` normal (no `tenants:migrate`, eso es solo para bases de tenant).

**Detalle real al implementarlo:** el modelo necesita `protected $guard_name = 'landlord';` explícito — sin esto, Spatie asume el guard por defecto (`web`) al crear/asignar roles, y `assignRole()`/`hasRole()` no matchean nada aunque las tablas y los datos existan. Tabla propia `admins` (migración `2026_08_28_100000_create_admins_table.php`, central) — separada de `users` a propósito, que ya solo existe por tenant desde REQ-1.7.

### 1.4 — Seeder del landlord (REQ-1.4)

`database/seeders/Landlord/` — `LandlordRoleSeeder` (rol `Super Admin`, `guard_name` `landlord`) + `LandlordAdminSeeder` (primer `Admin`, credenciales de arranque hardcodeadas `super@zertixpos.com`/`password`, mismo criterio que `Database\Seeders\Demo\UserSeeder` — cambiar antes de exponer el Panel de Súper Admin en producción) + `LandlordSeeder` que orquesta ambos. Se corre así, **nunca** con `db:seed` a secas:

**Por qué el `--class` es obligatorio, no opcional:** `db:seed` sin argumentos apunta siempre a `Database\Seeders\DatabaseSeeder` — que es el seeder de **negocio**, pensado para correr vía `tenants:seed` (REQ-1.7). Correrlo a secas contra la central rompe de inmediato, intenta poblar tablas (`clients`, `products`, etc.) que ahí no existen.

**Verificado con `tinker`:** `Admin::hasRole('Super Admin')` → `true`; idempotente (`firstOrCreate`), correrlo dos veces no duplica nada.

### 1.5 — Conexión de tenant en `.env`/`config/database.php` (REQ-1.5)

Confirmado contra la doc real de `stancl/tenancy`: no se necesitan variables nuevas en `.env`. El `.env` actual (`DB_HOST`/`DB_USERNAME`/`DB_PASSWORD`/`DB_PORT`) se queda tal cual — es la conexión landlord. `config/database.php` agrega una conexión plantilla que reusa esas mismas variables para host/usuario/contraseña, con `database => null` — el nombre de la base se setea en tiempo de ejecución por el paquete.

**Corrección al ejecutarlo (2026-08-28):** la plantilla **no se puede llamar `tenant`** — ese nombre está reservado por el paquete para la conexión dinámica que arma él mismo (advertido en el propio comentario de `config/tenancy.php`: *"don't name your template connection tenant. That name is reserved by package"*). Se creó como `'tenant_template'` en `config/database.php` (clon de `'mysql'`, mismo `driver`/charset/`options`, solo `database => null`) y se referenció explícito en `config/tenancy.php`: `'template_tenant_connection' => 'tenant_template'` (antes `null`, que caía por fallback implícito a la conexión `'mysql'` — funcionaba igual, pero no de forma explícita como pide el plan).

Si algún día se gradúa un tenant a un servidor físicamente distinto, esa excepción se guarda como campos (`tenancy_db_host`, etc.) en la fila de ese `Tenant`, nunca en `.env`.

**Verificado con `tinker`** dentro de `$tenant->run()` sobre el tenant `dev`: `config('database.default')` es `tenant` (la conexión ya armada por el paquete a partir de `tenant_template`), `host=mysql`, `database=tenantdev`, datos existentes intactos.

### 1.6 — Fix obligatorio: caché de permisos por tenant (REQ-1.6)

**No basta con `CacheTenancyBootstrapper` genérico de `stancl/tenancy`.** Ese bootstrapper cubre el caché normal de la app (Cache facade), pero `spatie/laravel-permission` mantiene su propio caché de roles/permisos a través de `PermissionRegistrar`, con su propia clave — el bootstrapper genérico no lo toca. **Confirmado el mecanismo exacto (2026-08-28), no solo la sospecha:** `PermissionRegistrar::__construct()` captura su propio `Illuminate\Cache\Repository` una sola vez, al boot de la app — **antes** de que la tenencia se inicialice — así que ni siquiera pasa por el swap de `CacheTenancyBootstrapper`. Sin este fix, el caché de permisos (24h por defecto, clave global `spatie.permission.cache`) es un único namespace compartido entre **todos** los tenants + el landlord — no una posibilidad teórica, una fuga de datos real confirmada con `tinker`.

**Implementado:** dos listeners nuevos en `app/Listeners/Tenancy/`:
- `SetTenantPermissionCacheKey` (`TenancyBootstrapped`): `$registrar->cacheKey = config('permission.cache.key').'.tenant.'.$tenant->getTenantKey()`.
- `ResetPermissionCacheKey` (`TenancyEnded`): vuelve a `config('permission.cache.key')` — importante para un worker de cola que procese varios tenants en el mismo proceso PHP, para que no arrastre la key del tenant anterior.

Registrados en `TenancyServiceProvider::events()`, junto a los que ya traía el paquete (`BootstrapTenancy`, `RevertToCentralContext`).

**Verificado con `tinker`:** dentro de `$tenant->run(...)`, `$registrar->cacheKey` es `spatie.permission.cache.tenant.dev`; fuera, vuelve a `spatie.permission.cache`.

**Verificación cruzada completa (2026-08-28), con un segundo tenant real (`test2`, creado y sembrado — ver `zertix:seed-demo` corrido vía `tenants:run`):**
```
tenant: dev   → db: tenantdev    → products: 23, sales: 103, users: 1 → cache key: spatie.permission.cache.tenant.dev
tenant: test2 → db: tenanttest2  → products: 23, sales: 100, users: 2 → cache key: spatie.permission.cache.tenant.test2
fuera de tenencia (central)      → cache key: spatie.permission.cache
```
Bases físicas distintas, conteos de negocio independientes, cache key de Spatie distinta por tenant y correctamente reseteada fuera de cualquier tenant — aislamiento real confirmado, no solo teórico.

### 1.7 — Mover las migraciones de negocio a `database/migrations/tenant/` (REQ-1.7)

**Corrección encontrada revisando la doc real de migraciones antes de arrancar (2026-08-27) — no estaba en el plan original.** `tenancy:install` crea la carpeta `database/migrations/tenant/` pero no mueve nada a ella; solo `create_tenants_table`/`create_domains_table` quedan (correctamente) en la raíz. La doc oficial es explícita: en modo multi-database, cualquier tabla que no sea del landlord tiene que vivir en `database/migrations/tenant/` y correr con `php artisan tenants:migrate`, no con `migrate` normal — `migrate` normal solo toca la conexión central.

**El problema real si se salta este paso:** hoy el proyecto tiene ~100 migraciones (usuarios, productos, ventas, inventario, clientes, POS, NCF, contabilidad — todo) en la raíz `database/migrations/`, corriendo contra la conexión central por defecto. Eso incluye `2025_12_06_155224_create_permission_tables.php`, la migración de Spatie que crea `roles`/`permissions`/`model_has_roles`/`model_has_permissions` para el guard `web` (los usuarios de negocio actuales, no el landlord). Si Fase 1 se ejecuta sin mover este directorio completo, el resultado sería: `tenants`/`domains` en modo tenant real, pero **todo el negocio (incluidos los roles de cada cliente) seguiría compartiendo una sola base central entre todos los tenants** — contradice directamente "cada cliente nuevo obtiene su propia base física".

**Qué se mueve, literal:** el directorio `database/migrations/` completo (menos `create_tenants_table.php`/`create_domains_table.php`, que se quedan en la raíz) pasa a `database/migrations/tenant/`. Se corre con `php artisan tenants:migrate` contra cada tenant, nunca con `migrate` a secas.

**Colisión de namespace — matiz confirmado al ejecutarlo (2026-08-27):** la preocupación de la doc genérica aplica a migraciones con `class NombreExplícito extends Migration`. La migración real de Spatie en este proyecto usa **clase anónima** (`return new class extends Migration`, estilo por defecto desde Laravel 9+) — no hay colisión de nombre de clase PHP. Alcanzó con copiar el archivo a la raíz con otro nombre de archivo/timestamp (`2026_08_27_130300_create_landlord_permission_tables.php`), sin renombrar ninguna clase.

**Seeders:** `PermissionSeeder`/`RoleSeeder`/`UserSeeder` de negocio (los que ya existen) pasan a ejecutarse vía `php artisan tenants:seed`, no `php artisan db:seed` — corren por tenant, no central. El landlord tiene su propio seeder aparte (REQ-1.4), ese sí con `db:seed`/`migrate` normal.

### 1.8 — Modelo `Tenant` propio + permisos de MySQL (REQ-1.8)

**Encontrado al sembrar el primer tenant de desarrollo (2026-08-28).** El `tenant_model` que deja `config/tenancy.php` por defecto es `Stancl\Tenancy\Database\Models\Tenant` — ese modelo base **no** implementa `TenantWithDatabase`, así que crear un tenant con él falla con `TypeError` al intentar provisionar la base física (`CreateDatabase` job). Confirmado contra la doc real de "Tenants": hay que crear `App\Models\Tenant` a mano:

```php
<?php

namespace App\Models;

use Stancl\Tenancy\Contracts\TenantWithDatabase;
use Stancl\Tenancy\Database\Concerns\HasDatabase;
use Stancl\Tenancy\Database\Concerns\HasDomains;
use Stancl\Tenancy\Database\Models\Tenant as BaseTenant;

class Tenant extends BaseTenant implements TenantWithDatabase
{
    use HasDatabase, HasDomains;
}
```

Registrado en `config/tenancy.php` (`'tenant_model' => Tenant::class`, con el `use App\Models\Tenant;` correspondiente).

**Segundo bloqueo, infra local:** el usuario `sail` de la instancia MySQL de Docker (`docker-compose.yaml`) solo tenía `GRANT ALL PRIVILEGES` sobre `gestionventas_dev`/`testing%` — no puede crear/borrar las bases `tenant<id>` que el paquete provisiona dinámicamente por cada tenant (`DROP DATABASE`/`CREATE DATABASE` fallan con "Access denied"). Se le agregó, contra la instancia local de desarrollo (no aplica a producción, donde el usuario de MySQL se aprovisiona distinto):

```sql
GRANT ALL PRIVILEGES ON `tenant%`.* TO 'sail'@'%';
FLUSH PRIVILEGES;
```

### 1.9 — Tablas base de Laravel también en la central (REQ-1.9)

**Mismo problema de fondo que 1.7, encontrado al probar el primer tenant real (2026-08-28) — pero con las tablas del propio framework, no las de negocio.** El grupo de middleware `web` (que trae `StartSession`, y cualquier operación de caché) corre en `routes/tenant.php` **antes** de `InitializeTenancyByDomain` — el orden del array `['web', InitializeTenancyByDomain::class, ...]` importa, Laravel expande `web` en el lugar donde aparece. Eso significa que `SESSION_DRIVER=database`/`CACHE_STORE=database` siempre leen/escriben contra la conexión **central** en ese punto del pipeline, sin importar si la ruta termina siendo de un tenant.

Como `sessions`/`cache`/`jobs` (bundle original de Laravel) se movieron enteros a `database/migrations/tenant/` en REQ-1.7, la central se quedó sin ninguna — **hasta la ruta `/` del dominio central reventaba** con `Base table or view not found: sessions` apenas se corrió `migrate:fresh` sobre la central.

**Superado por REQ-1.12 (2026-08-28):** al migrar `cache`/`session`/`queue` a Redis, las migraciones centrales duplicadas para estas 3 tablas se volvieron innecesarias — ver §1.12 para el detalle final (qué se borró, qué quedó).

### 1.10 — `EnsureInstallationWizardCompleted` fuera del grupo `web` global (REQ-1.10)

**Encontrado en la misma sesión de pruebas (2026-08-28), mismo mecanismo que 1.9.** Este middleware (de la v1.1.0 Fase 8, pensado para una sola instalación) estaba anexado al grupo `web` global en `bootstrap/app.php`.
```php
Route::middleware([
    'web',
    InitializeTenancyByDomain::class,
    PreventAccessFromCentralDomains::class,
    EnsureInstallationWizardCompleted::class, // después de InitializeTenancyByDomain, a propósito
])->group(function () { /* ... */ });
```

**Efecto secundario esperado, no un bug nuevo que arreglar ahora:** `/install` (el wizard viejo) sigue en `routes/web.php`, sin `InitializeTenancyByDomain` — queda confirmado roto (intenta escribir `users`/`configuraciones_generales`/consultar `provinces` contra la central, que no las tiene). Es exactamente el trabajo que `REQ-4.1` ya tenía asignado ("envuelve este wizard para el flujo multi-tenant") — no se toca en Fase 1. Para poder seguir probando localmente sin pasar por el wizard, se creó un admin manual dentro de la base del tenant `dev` por `tinker` (`$tenant->run(fn () => ...)`, `nombre_empresa` seteado a mano + usuario + rol) — solo desarrollo, no un flujo real.

### 1.12 — Redis para caché/sesión/cola (REQ-1.12)

**Decisión 2026-08-28, después de confirmar en código (no solo en teoría) que `CacheTenancyBootstrapper` — ya activo en `config/tenancy.php` — es incompatible con `CACHE_STORE=database`.** El mecanismo de aislamiento por tenant de ese bootstrapper (`Stancl\Tenancy\CacheManager::__call()`) envuelve *toda* llamada al facade `Cache::` en `.tags([...])`; `Illuminate\Cache\DatabaseStore` no implementa la interfaz taggable, así que `Repository::tags()` tira `BadMethodCallException: This cache store does not support tagging` apenas se ejecuta. No es hipotético: `App\Models\Sales\Pos\PosSetting::getSettings()` y `App\Models\Accounting\AccountingAccountRole` ya usan `Cache::rememberForever()` directo — sin este fix, abrir un terminal POS o calcular algo contable en cualquier tenant real revienta garantizado.

**Instalado:**
- Servicio `redis` (`redis:alpine`) agregado a `docker-compose.yaml`, con volumen propio (`sail-redis`) y healthcheck.
- `.env`: `REDIS_CLIENT=phpredis` (la extensión ya viene compilada en la imagen de Sail, `docker/8.4/Dockerfile:40` — sin necesidad de `composer require predis/predis`), `REDIS_HOST=redis` (nombre del servicio Docker, no `127.0.0.1`), `SESSION_DRIVER=redis`, `CACHE_STORE=redis`, `QUEUE_CONNECTION=redis`.

**Efecto sobre REQ-1.9:** las migraciones centrales de `cache`/`sessions` (REQ-1.9) dejaron de hacer falta — se borraron. `jobs`/`job_batches` tampoco (Redis guarda las colas él mismo, y `Bus::batch()` no se usa en el proyecto) — la migración se recortó a solo `failed_jobs`, que Laravel sigue consultando contra la conexión activa sin importar el driver de cola (`config/queue.php`).

**Redis no reemplaza REQ-1.6, resuelven problemas distintos:** Redis hace que `.tags()` funcione de verdad para el resto de la app (`PosSetting`, `AccountingAccountRole`, cualquier `Cache::` futuro). Pero Spatie, como se documentó en §1.6, ni siquiera pasa por ese mecanismo — captura su propio `Repository` al boot. El listener de REQ-1.6 sigue siendo obligatorio con o sin Redis.

**Verificado con `tinker`:** `PosSetting::getSettings()` ya no revienta dentro de `$tenant->run(...)` (antes tiraba `BadMethodCallException` garantizado).

### 1.13 — La ruta de actualización de Livewire no inicializa tenancy (REQ-1.13)

**Encontrado probando la UI real de un tenant (2026-08-28), después del cierre inicial de la fase.** Livewire registra su propia ruta de actualización AJAX (`POST /livewire-{hash}/update`, nombre `default-livewire.update`) automáticamente al boot, en `Livewire\Mechanisms\HandleRequests\HandleRequests::boot()`, con **solo** `->middleware('web')` — confirmado leyendo el código fuente del paquete. Esa ruta nunca pasa por `routes/tenant.php`, así que **nunca** corría `InitializeTenancyByDomain`.

**Consecuencia real, reproducida antes del fix:** la carga inicial (GET) de cualquier página con un componente Livewire funciona bien (esa sí está bajo `routes/tenant.php`), pero **cualquier interacción posterior** (`wire:click`, `wire:model.live`, cualquier `$set`, incluido el tab "Papelera" de las tablas migradas en Fase 0) disparaba un POST a esa ruta sin tenencia inicializada — el guard `web` intentaba resolver `Auth::user()` contra la conexión **central**, que no tiene tabla `users` (es de negocio, solo por tenant desde REQ-1.7). Resultado: `SQLSTATE[42S02]: Base table or view not found: 'users'` en **cualquier** acción Livewire sobre un tenant, no un caso aislado de una vista con papelera — el 100% de los módulos migrados en Fase 0 comparten esa misma ruta, así que bloqueaba de hecho toda la UI interactiva del sistema en un tenant real.

**Fix implementado, en `App\Providers\TenancyServiceProvider::bootLivewireUpdateRoute()`:**

```php
Livewire::setUpdateRoute(function ($handle) {
    return Route::post('/livewire/update', $handle)
        ->middleware(['web', Middleware\InitializeTenancyByDomain::class])
        ->name('tenant.livewire.update');
});

Middleware\InitializeTenancyByDomain::$onFail = function ($exception, $request, $next) {
    if (in_array($request->getHost(), config('tenancy.central_domains'), true)) {
        return $next($request);
    }

    throw $exception;
};
```

**Por qué sin `PreventAccessFromCentralDomains`:** esta misma ruta también la va a necesitar el futuro Panel de Súper Admin (Fase 5), que corre en el dominio central — esa middleware la bloquearía ahí. `InitializeTenancyByDomain` sola, con `$onFail` sobreescrito, resuelve el resto: si el dominio matchea un tenant, inicializa normal; si el dominio es central, continúa sin inicializar (caso esperado, no un error); si el dominio no es ni tenant ni central (typo, subdominio no registrado), sigue relanzando la excepción — no se relaja esa protección para el caso raro.

**No hace falta llamar a `setUpdateRoute()` antes de que Livewire registre la suya** — `Livewire::setUpdateRoute()` simplemente registra una ruta adicional con otro nombre, y `HandleRequests::getUpdateUri()` prioriza cualquier ruta `*livewire.update` que no sea la `default-livewire.update` al armar la URL que el frontend usa. El orden de boot entre `TenancyServiceProvider` y el provider de Livewire no importa.

**Verificado en el navegador real, no solo con `tinker`:** login en `dev.localhost:8082`, clic en el tab "Papelera" de Terminales POS (`App\Livewire\App\Sales\PosTerminalTable`) — la petición de red muestra `POST http://dev.localhost:8082/livewire/update → 200 OK`, la tabla cambia a la vista de papelera sin ningún error de `users`/`SQLSTATE`. Confirmado también con `Livewire::getUpdateUri()` vía `tinker`: devuelve `/livewire/update` (la ruta propia), no la de Livewire.

### 1.14 — `asset_helper_tenancy` rompe assets estáticos + archivos por tenant referenciados mal (REQ-1.14)

**Encontrado probando la UI real de un tenant (2026-08-28), mismo día que REQ-1.13 — el favicon y el logo del sidebar no cargaban en `dev.localhost`.** No era el symlink de `storage:link` (se confirmó con `readlink` que sigue apuntando bien) — el problema es `config/tenancy.php` con `'asset_helper_tenancy' => true` (default del paquete, el propio comentario del archivo ya advertía del riesgo).

**El mecanismo, completo:** `stancl/tenancy` trae dos piezas distintas para archivos:
- **`tenant_asset($path)`** (helper) → `route('stancl.tenancy.asset', ['path' => $path])` → `/tenancy/assets/{path}` → `Stancl\Tenancy\Controllers\TenantAssetsController::asset()`, que hace `response()->file(storage_path("app/public/$path"))`. Como `storage_path()` ya viene sufijado por tenant (`FilesystemTenancyBootstrapper`, `suffix_storage_path`), este controlador sirve el archivo de la carpeta física correcta de cada tenant — sin depender de ningún symlink en `public/`. Es el mecanismo correcto para lo que un tenant sube de verdad (su logo de empresa).
- **`asset_helper_tenancy => true`** hace algo distinto y más agresivo: reescribe la **raíz** del helper genérico `asset()` para que **cualquier** llamada, en toda la app, pase por esa misma ruta `/tenancy/assets/*` — incluidos archivos estáticos de `public/img/` (favicon, logo del sidebar, build de Vite) que son iguales para todos los tenants y nunca estuvieron en `storage/app/public`. Esas llamadas terminan pidiendo un archivo que no existe ahí → 404 (confirmado en la consola del navegador).

**Fix:** `'asset_helper_tenancy' => false` en `config/tenancy.php` — `asset()` vuelve a comportarse normal (apunta a `public/` directo), y `tenant_asset()` queda disponible aparte para lo que sí es específico de un tenant.

**Auditoría de todo lo que referenciaba `$config->logo`/imágenes de producto (no solo el favicon) — 3 patrones más rotos bajo tenencia, ninguno cubierto por el flag de arriba:**

1. **Logo de empresa vía `asset('storage/'.$config->logo)`** (`configuration/general/edit.blade.php`, `sales/pos/sessions/formats/ticket.blade.php`) — apunta al symlink `public/storage` (central, sin sufijo). Cambiado a `tenant_asset($config->logo)`.
2. **Logo en PDFs generados con DomPDF vía `public_path('storage/'.$config->logo)`** (`sales/invoices/formats/full.blade.php`, `sales/pos/sessions/formats/full.blade.php`, `sales/quotes/formats/pdf.blade.php`, `finance/collections/pdf.blade.php`) — DomPDF necesita una ruta de archivo local, no una URL (`enable_remote => false` por defecto en `config/dompdf.php`, confirmado contra el paquete — no acepta URLs remotas salvo que se active a propósito, y activarlo es justo lo que el propio README de `barryvdh/laravel-dompdf` marca como "usar con precaución"); `public_path()` siempre resuelve contra `public/` (central), nunca contra la carpeta sufijada del tenant. Corregido a `storage_path('app/public/'.$config->logo)`.

   **Hallazgo adicional al revisar esto (2026-08-28, reportado por el usuario con una factura real donde el logo salía roto):** `sales/invoices/formats/full.blade.php` y `finance/collections/pdf.blade.php` se renderizan en **dos contextos distintos** — DomPDF (`InvoicePrintService`/`CollectionPrintService`, necesita la ruta local) **y** vista previa en pantalla (`InvoiceController`/`CollectionController`, `view(...)->render()` directo al navegador — necesita una URL real, una ruta de archivo del servidor no es un `src` válido). Poner `storage_path(...)` a secas arregla el PDF descargado pero rompe la vista previa (exactamente el ícono roto reportado). Se resolvió con `$logoSrc` opcional pasado por quien llama: el `@php` de cada vista hace `$logoSrc ??= tenant_asset($config->logo)` (default seguro, sirve para la vista previa); `InvoicePrintService::generateLetterPDF()`/`CollectionPrintService::generateLetterPDF()` (la rama DomPDF) pasan `$logoSrc` explícito con `storage_path(...)` para sobreescribir ese default. `sales/pos/sessions/formats/full.blade.php` y `sales/quotes/formats/pdf.blade.php` no tienen este problema — confirmado que solo se renderizan vía DomPDF, nunca como vista previa, así que se quedan con `storage_path()` fijo.

   **Verificado con `tinker`** (dentro de `$tenant->run()`): `tenant_asset($config->logo)` genera una URL válida y `storage_path('app/public/'.$config->logo)` apunta a un archivo que sí existe físicamente en `storage/tenantdev/...`. Nota sobre el propio `tinker`: corrido desde CLI (sin contexto de request HTTP real) el host de la URL cae al `APP_URL` de `.env` en vez del dominio del tenant — no es un bug, es el comportamiento esperado de Laravel fuera de un request real; confirmado en el log de red del navegador (sesión anterior) que dentro de un request real la URL sí sale con el host correcto (`dev.localhost:8082`).
3. **`Product::getImageUrlAttribute()`** construía `'/storage/'.$this->image_path` a mano — ni `asset()` ni `tenant_asset()`, bypaseaba cualquier mecanismo. El comentario original explicaba que era así a propósito para evitar romperse cuando el puerto real difería de `APP_URL` (bug ya resuelto en REQ-1.11). Cambiado a `route('stancl.tenancy.asset', ['path' => $this->image_path], false)` — tercer argumento `false` para mantener la misma URL relativa que tenía antes (sin depender de `APP_URL`), pasando ahora por la ruta que sí resuelve el archivo del tenant correcto.

**Revisado y descartado — no hay nada más que arreglar hoy:** no existe todavía ningún enlace público de PDF pensado para compartir (ej. por WhatsApp a futuro) — ni rutas firmadas (`signedRoute`) ni descargas públicas de facturas/cotizaciones en el código actual. Cuando se construya esa función, tiene que nacer usando `tenant_asset()`/la ruta de assets del tenant (o una ruta propia envuelta en `InitializeTenancyByDomain`), nunca un link estático tipo `public_path()`/`/storage/...` a mano — para no repetir el mismo error encontrado acá.

**Efecto secundario encontrado de paso:** `FilesystemTenancyBootstrapper` crea `storage/tenant<id>/` en disco la primera vez que un tenant sube algo (logo, imagen de producto) — ese directorio no estaba en `.gitignore` (el proyecto nunca había tenido storage por-tenant antes de esta fase). Se agregó `/storage/tenant*` al `.gitignore`, mismo criterio que ya cubre `/public/storage`.

**Grep de verificación final:** `public_path('storage`, `asset('storage`, y `'/storage/'.` a mano — cero resultados en todo `app/`/`resources/views` después del fix.

### 1.15 — Rutas gateadas por módulo evaluadas antes de que la tenencia se inicialice (REQ-1.15)

**Encontrado por el usuario probando en base de datos + UI reales, activando el módulo NCF (2026-08-28) — `Route [finance.ncf.sequences.index] not defined`, y `route:list` mostraba `ANY app/finance/ncf/{any?}` en vez de las rutas reales.**

**Causa raíz, mismo mecanismo estructural que REQ-1.9/1.10/1.13 pero en una capa distinta — el registro de rutas, no un middleware.** `routes/app/finance.php` y `routes/app/reports.php` gateaban las rutas de NCF así:

```php
if (module_enabled('sales.ncf')) {
    Route::prefix('ncf')->name('ncf.')->group(function () { /* rutas reales */ });
} else {
    Route::any('ncf/{any?}', fn () => redirect(...)); // fallback
}
```

Ese `if` corre **una sola vez, al registrar las rutas** — `TenancyServiceProvider::mapRoutes()` carga `routes/tenant.php` (que incluye `routes/app/*.php`) dentro de `$this->app->booted(...)`, y el registro de rutas **siempre** ocurre antes de que Laravel pueda despachar la petición a un middleware — no hay forma de que `InitializeTenancyByDomain` ya haya corrido para esa misma petición en ese punto. Así que `module_enabled('sales.ncf')` ahí consultaba siempre la conexión central, que no tiene `installation_modules` (es de negocio, solo por tenant desde REQ-1.7) — cae en `false` de forma determinística, el 100% de las veces, sin importar lo que diga el tenant real. Las rutas reales de NCF nunca llegaban a existir en la tabla de rutas bajo tenencia.

**Por qué otros módulos sí funcionaban (`accounting.advanced`, `sales.receivables`, en los mismos archivos):** esos usan `Route::middleware('module:xxx')` — el chequeo real vive dentro de `App\Http\Middleware\EnsureModuleEnabled`, que corre en tiempo de **despacho** de la petición (después de que `InitializeTenancyByDomain` ya inicializó la tenencia), no en tiempo de registro. La diferencia entre "middleware" y "`if` directo en el archivo de rutas" es exactamente lo que separaba un patrón que funciona de uno que no.

**Fix:** convertir NCF al mismo patrón de middleware que ya usan los otros módulos — `Route::middleware(['auth', 'permission:manage ncf sequences', 'module:sales.ncf'])` envolviendo el grupo completo, sin ningún `if`/`else` en el archivo de rutas. El fallback amigable (redirect con mensaje) se reemplaza por el 404 plano de `EnsureModuleEnabled` — mismo comportamiento que ya tienen `accounting.advanced`/`sales.receivables`, consistente con el resto del proyecto en vez de un caso especial.

**Verificado con `tinker`** dentro de `$tenant->run()` sobre el tenant `dev`: `module_enabled('sales.ncf')` → `true`, `route('finance.ncf.sequences.index')` resuelve una URL real. Confirmado también con `route:list`: `finance.ncf.sequences.*`, `finance.ncf.logs.*`, `finance.ncf.types.*` y `reports.ncf` aparecen con sus nombres reales, sin el `ANY .../{any?}` de antes.

**Para no repetirlo:** cualquier gate de módulo futuro en `routes/app/*.php` tiene que ser `Route::middleware('module:xxx')`, nunca un `if (module_enabled(...))`/`if (general_config()...)` evaluado directo en el archivo de rutas — ese patrón es estructuralmente incompatible con tenencia por dominio, no es un detalle de NCF.

### 1.16 — `@auth` en `welcome.blade.php` intenta resolver un guard que no existe en central (REQ-1.16)

**Encontrado por el usuario visitando `localhost:8082/` (dominio central) con una cookie "recordarme" de una sesión previa en un tenant** — `SQLSTATE[42S02]: Base table or view not found: 'users'`, mismo mensaje que los hallazgos anteriores pero en un lugar nuevo: la vista `welcome.blade.php` (scaffold por defecto de Laravel, sin tocar hasta ahora).

**Causa:** `@auth` (línea 26) es azúcar de Blade para `Auth::check()` contra el guard por defecto — `web`. El guard `web` resuelve usuarios contra `App\Models\User`, que desde REQ-1.7 **solo existe por tenant**. `/` vive en `routes/web.php`, central, sin `InitializeTenancyByDomain` — así que `Auth::check()` ahí siempre consulta la conexión central. Con una cookie `remember_web_*` presente (de un login real en `dev.localhost`, que el navegador conserva), `SessionGuard` intenta resolver el usuario recordado vía `EloquentUserProvider::retrieveByToken()` contra `users` en la central, que no existe.

**No es un caso aislado de esta vista — es estructural:** el guard `web` **nunca** puede tener una sesión válida en una ruta central, sin importar qué tan simple sea la página. Cualquier `@auth`/`@guest`/`Auth::check()`/`Auth::user()` en una vista servida por `routes/web.php` está mal, no solo esta.

**Fix:** se quitó el `@auth`/`@else`/`@endauth` de `welcome.blade.php` — la página ya no intenta preguntar si "hay alguien logueado" en el sentido de negocio, siempre muestra el estado de invitado. De paso se eliminó el bloque muerto de `@if (Route::has('register'))` (esa ruta ya no existe desde v1.2.0 Fase 7.11). Es un placeholder hasta que Fase 4/5 construyan el landing real del dominio central — no una re-escritura de la página.

## Fase 2 — Roles y Permisos: convención `recurso.accion` (REQ-2)
**Rama:** `feature/v1.3.0-permissions-rename`

### Por qué ahora, y no junto con Multi-tenant en sí

No depende técnicamente de la Fase 1 — es trabajo puro sobre la conexión de tenant. Se hace en este punto del roadmap para que los permisos nuevos que la Fase 4 (Wizard) y Fase 5 (Súper Admin) van a necesitar (`manage_tenants`, `manage_billing`, etc.) nazcan ya sobre la convención correcta, en vez de mezclarse con la convención vieja y tener que renombrar dos veces.

**Cifra real, no la estimación original:** son 102 permisos, no ~90 — contados directo del array de `PermissionSeeder.php` (dashboard 1 + roles 5 + users 5 + config 4 + clients 7 + pos_points 6 + equipment 6 + products 8 + inventory 7 + accounting 23 + sales 15 + pos_terminals 15).

**`PermissionSeeder.php` reescrito completo (2026-08-28)** con la convención nueva — un permiso por `recurso.accion`, sin mezclar los dos estilos viejos ("roles index" vs "view products"). El array externo del seeder se reorganizó para que cada sección sea exactamente un `recurso` (antes agrupaba varios recursos sueltos bajo una sola clave de conveniencia, ej. `clients` incluía `configure business types`/`configure equipment types`, que ahora son sus propios grupos `business_types`/`equipment_types`). **Hallazgo adicional al hacer el rename, no anticipado:** `view payments`/`create payments`/`edit payments`/`cancel payments`/`delete payments`/`export payments`/`print payment receipts` en realidad protegen `CollectionController` (Cobros) — confirmado en `routes/app/finance.php`, que ya traía el comentario admitiendo la deuda: el rename "Pagos"→"Cobros" de v1.2.0 REQ-4.1 nunca tocó estos nombres de permiso ("problema de datos aparte de la reestructuración"). ### 2.2 — Redundancias y ubicaciones corregidas (REQ-2.2)

**Va antes que el script de REQ-2.3 a propósito (reordenado 2026-08-28) — no después.** Estas correcciones tienen que estar aplicadas en `PermissionSeeder.php` **antes** de generar la tabla de mapeo nombre-viejo→nombre-nuevo que el script de REQ-2.3 va a usar contra los 214 usos reales. ### 2.6 — Traducción: port exacto del helper real de Orvian (REQ-2.6)

`Laravel-Lang/lang` (confirmado compatible con Laravel 12, cubre `validation`/`auth`/`passwords`/`pagination`) para los strings propios del framework — complementa, no reemplaza, lo de abajo.

**El helper real de Orvian** (`orvian/app/Helpers/PermissionHelper.php`, compartido por el usuario) recibe **dos argumentos**, no uno, porque cada permiso tiene tanto un `label` (texto corto del checkbox) como una `description` (texto de ayuda debajo):

```php
<?php

use Illuminate\Support\Facades\Lang;

if (!function_exists('trans_permission')) {
    function trans_permission(string $name, string $key = 'label'): string
    {
        $langKey = "permissions.{$name}.{$key}";

        if (Lang::has($langKey)) {
            return __($langKey);
        }

        return ucfirst(str_replace(['.', '_'], ' ', $name));
    }
}
```

**Port a ZertixPOS — literal, sin reescribir la lógica.** Sigue la convención ya establecida en este proyecto (`app/Helpers/general.php`/`pos_helper.php`/`module_helper.php`, un array `autoload.files`, cada helper con su `if (! function_exists(...))`):

1. Crear `app/Helpers/permission_helper.php` con el contenido de arriba, tal cual.
2. Agregar `"app/Helpers/permission_helper.php"` al array `autoload.files` de `composer.json`, junto a los otros 3.
3. `composer dump-autoload`.

`lang/es/permissions.php` tiene que traer **ambas** claves por permiso (`label` y `description`), no solo `label` — el helper las pide separadas. **Importante: la estructura tiene que ir anidada por segmento de punto** (`'sales' => ['create' => ['label' => ..., 'description' => ...]]]`), no como key plana `'sales.create' => [...]` — Laravel resuelve `permissions.sales.create.label` recorriendo niveles anidados del array (`Arr::get` con `explode('.', $key)`), no comparando una key literal con puntos. El primer intento usó keys planas y `Lang::has()` devolvía `false` en silencio para las 82 activas, cayendo siempre al fallback.

**Wireado (2026-08-28) en la vista real de gestión de roles/permisos** (`resources/views/roles/permissions.blade.php`, donde antes vivía el bug de `explode('.', $permission->name)[1]` que nunca funcionó — ver REQ-2.1): `label="{{ trans_permission($permission->name) }}"` y `description="{{ trans_permission($permission->name, 'description') }}"` en el `x-ui.forms.checkbox` de cada permiso (el componente ya soportaba `description` como texto de ayuda, no hizo falta tocarlo). 3. **`SoftDeletes` en `User` (tenant) y `Admin` (landlord) por igual — confirmado con un error real, no una sospecha. Implementado (2026-08-29).** Reproducido borrando un usuario con historial real en `test2.localhost`:
   ```
   SQLSTATE[23000]: Integrity constraint violation: 1451 Cannot delete or update a parent row:
   a foreign key constraint fails (`tenanttest2`.`payments`, CONSTRAINT `payments_created_by_foreign`
   FOREIGN KEY (`created_by`) REFERENCES `users` (`id`))
   ```
   `UserController::destroy()` hace `$user->delete()` — un `DELETE` real, porque `App\Models\User` no tiene el trait `SoftDeletes`. Cualquier usuario con actividad real (ventas, cobros, sesiones de caja, movimientos — todo lo que guarda `created_by`/`user_id`) revienta al borrarlo, porque esas tablas referencian `users.id` por FK sin `onDelete('cascade')` ni `nullOnDelete()` — **y no deberían tenerlo**: `created_by` es una relación de auditoría ("quién lo hizo"), no de propiedad ("a quién pertenece") — un `Payment`/`Sale` es del negocio, no del cajón que lo registró. No hay hoy un requisito de "derecho al olvido" (borrado real de PII) sobre la mesa, y de existir a futuro probablemente ni aplicaría del todo dado el punto anterior (retención fiscal) — así que no se construye el hueco para algo que no se necesita y que, si se necesitara, no sería un `forceDelete()` simple sino una anonimización real (reemplazar nombre/email, conservar el historial). ## Fase 3 — Modelo de suscripción, pasarela de pago y middleware de corte (REQ-3)
**Rama:** `feature/v1.3.0-subscriptions`

### Por qué un modelo de fechas, no un flag de estado

Depender solo de un `subscription_status` que un webhook actualiza es frágil: si el webhook de PayPal no llega (caída momentánea, reintento fallido), el flag se queda congelado en `current` para siempre y el cliente sigue con acceso aunque ya no pague. La forma robusta es que el middleware compare contra una fecha guardada, no contra un estado empujado.

### 3.1 — Tabla `subscriptions` (REQ-3.1)

Landlord: `id`, `tenant_id`, `plan_id` (con qué plan corre este ciclo — permite historial si sube/baja de plan), `gateway`/`gateway_subscription_id`, `status` (`active`/`past_due`/`cancelled`/`paused`, el estado crudo que reporta PayPal), `starts_at`, **`current_period_ends_at`** (el campo que el middleware realmente consulta), `cancelled_at` (nullable, conserva el historial).

**Fix real encontrado al implementar, no anticipado en el diseño original:** `Subscription`/`SubscriptionInvoice` corrían el riesgo de leer la conexión de base equivocada cuando el código corre "dentro" de un tenant (ej. el middleware de REQ-3.5, que se ejecuta en cada request de un tenant) — sin fijar la conexión, esos modelos habrían intentado resolver `subscriptions` contra la base del tenant activo en ese momento, no contra landlord. Mismo patrón que ya se documentó para `Plan` en REQ-3.4: `protected $connection = 'landlord'` explícito en ambos modelos.

**Implementado (2026-08-29):** `database/migrations/2026_08_29_100000_create_subscriptions_table.php` + `App\Models\Landlord\Subscription`. `tenant_id` es `string` con FK real a `tenants.id` (la PK de Tenant es string, no autoincremental — `foreignId()` no aplica, se usa `$table->string('tenant_id')` + `$table->foreign(...)` a mano). `plan_id` queda **sin FK** a propósito: `plans` todavía vive en la base de cada tenant (REQ-3.4 lo mueve a landlord más adelante), y una FK cruzada entre bases físicas distintas no es posible en MySQL. `status` agrega `trialing` como valor por defecto (no estaba en la lista original de REQ-3.1, lo incorpora REQ-3.8) — mismo esquema de fechas sirve para ambos casos, no hace falta una migración de alteración aparte cuando se implemente el trial. Verificado con `migrate --pretend` (SQL generado) y `migrate` real contra la base landlord de desarrollo.

### 3.5 — Middleware por fecha (REQ-3.5)

El middleware nunca depende de que el webhook haya avisado a tiempo.

**Implementado (2026-09-01):** `app/Http/Middleware/Billing/EnsureSubscriptionActive.php`, registrado en `routes/tenant.php` justo después de `EnsureInstallationWizardCompleted` (mismo razonamiento: necesita `tenant()` ya resuelto). **Bug real encontrado en vivo (2026-09-06), probando el Escenario B de REQ-4.8 con un tenant creado por el Wizard (trial real, no un tenant sembrado a mano):** `routes/auth.php` (incluye `login`) se registra DENTRO del mismo grupo de middleware que este archivo protege (`routes/tenant.php`), así que sin excepción también quedaba bloqueado. Antes esto no se había notado porque el punto 1 de la verificación de arriba ("bloquea incluso antes de llegar a `/login`") se probó siempre con una sesión ya autenticada o sembrando la `Subscription` a mano — nunca con un visitante real, sin sesión, cuyo trial recién venció. El resultado real: `billing.past-due.blade.php` sin `auth()->check()` apunta su botón a `route('login')`, que el propio middleware vuelve a mandar a `billing.past-due` — un loop cerrado, sin ninguna forma de entrar a pagar.

**Primer fix, incompleto:** bypass por nombre de ruta (`routeIs`) para `login`/`logout`/`password.*`/`verification.*`. Arregló el link "Iniciar sesión" (la ruta `GET login` sí tiene ese nombre) pero el loop seguía — el usuario lo reprodujo de nuevo, esta vez llegando al formulario pero sin autenticar nunca. Causa real, confirmada con `curl` crudo (sin la ambigüedad de un navegador real): `Route::post('login', ...)` (`routes/auth.php:17`) y `Route::post('confirm-password', ...)` (línea 47) **no tienen `->name(...)`** — el bypass por nombre nunca los alcanzaba, así que el `POST /login` con credenciales correctas seguía cortado por el middleware ANTES de que `AuthenticatedSessionController::store()` corriera `Auth::attempt()` — el formulario "andaba" (302) pero jamás autenticaba a nadie de verdad.

**Fix real:** el chequeo pasó de comparar por nombre de ruta a comparar por **path** (`$request->is('login', 'logout', 'confirm-password', 'forgot-password', 'reset-password*', 'verify-email*', 'email/verification-notification', 'password')`) — cubre ambos verbos (GET/POST) de cada ruta de `routes/auth.php`, tengan nombre o no. Verificado con `curl` de punta a punta: `POST /login` con credenciales válidas ahora sí redirige a `/dashboard` (antes: directo a `/suscripcion/vencida` sin autenticar), `GET /dashboard` con la suscripción vencida redirige correctamente a `/suscripcion/vencida`, y esa pantalla ya muestra "Regularizar pago" (antes: "Iniciar sesión" en loop).

**Hallazgo aparte, no relacionado a este bug, encontrado depurando el mismo flujo: sesiones sin aislar por tenant en Redis.** `SESSION_DRIVER=redis` pero `RedisTenancyBootstrapper` estaba comentado en `config/tenancy.php` — a diferencia de `Cache::get()/put()` (sí aislados, vía `CacheTenancyBootstrapper`/`Stancl\Tenancy\CacheManager::__call()`), la sesión resuelve su store con `Cache::store('redis')` internamente (`Illuminate\Session\SessionManager::createCacheHandler()`), y `->store()` es un método real de `CacheManager` que **no pasa por el `__call()`** que aplica el tag de tenant — devuelve el repositorio crudo, sin tag. Resultado: las claves de sesión de todos los tenants vivían mezcladas en el mismo namespace de Redis (`zertixpos-database-zertixpos-cache-*`, sin ningún prefijo de tenant), distinguibles solo por el ID de sesión aleatorio — no una fuga activa (nadie puede adivinar la sesión de otro), pero sí un hueco de aislamiento operativo real. **Activado (2026-09-06):** `RedisTenancyBootstrapper` descomentado en `bootstrappers`, `'default'` (la conexión que usa la sesión) agregado a `redis.prefixed_connections`. Requiere phpredis — ya confirmado instalado y en uso (`REDIS_CLIENT=phpredis`). Verificado en vivo: una sesión nueva después del cambio quedó con la clave `tenant{id}zertixpos-cache-...` en vez de la genérica de antes. Sin impacto de rendimiento (la opción se fija una vez por request, a nivel de cliente phpredis, no por comando).

### 3.8 — Trial de 15 días + retención de 90 (REQ-3.8)

### 3.12 — Job de borrado automático (REQ-3.12)

Comando programado diario: busca tenants con `scheduled_deletion_at <= now()` y los borra. **Dos pasos, no uno** — confirmado contra la doc real de `stancl/tenancy`: `$tenant->delete()` por sí solo **no** borra la base de datos física, solo la fila `tenants`. Hay que tener registrado `Stancl\Tenancy\Jobs\DeleteDatabase` en el pipeline de eventos de `config/tenancy.php` (evento `TenantDeleted`) para que el borrado de la fila dispare también el borrado real de la base — si no, quedan bases huérfanas consumiendo espacio indefinidamente.

**Precaución encontrada en un issue real del paquete:** hay reportes de que `tenant()->delete()` puede colgarse en tenancy multi-base. Antes de dejar este job corriendo en automático contra tenants reales, probarlo primero contra el tenant de desarrollo (`dev.localhost`) y confirmar que termina limpio, con logging explícito de cada tenant borrado (nombre, fecha, motivo) antes de ejecutar el borrado — es una acción destructiva e irreversible, no debe fallar en silencio ni sin rastro.

**Implementado (2026-09-03):** `app/Console/Commands/Billing/PruneExpiredTenants.php` (`tenants:prune-expired`) — confirma primero que `Stancl\Tenancy\Jobs\DeleteDatabase` ya estaba registrado en el pipeline de `TenantDeleted` desde REQ-1.1 (no hacía falta agregarlo, solo verificarlo); loggea cada tenant (id, `scheduled_deletion_at`, `business_name`) **antes** de borrar, vía `Log::warning()`; excluye `is_demo` explícitamente aunque hoy nunca debería tener `scheduled_deletion_at` (defensa en profundidad); cada borrado va en su propio `try/catch` para que un fallo puntual no frene el resto de la corrida.

**No probado contra `dev`/`test2`/`demo`** (esos son los tenants de desarrollo reales, no un descartable) — en su lugar se creó un tenant desechable (`throwaway-prune-test`, base física `tenantthrowaway-prune-test` confirmada real con `SHOW DATABASES`), se le forzó `scheduled_deletion_at` en el pasado, y se corrió el comando: terminó limpio (sin colgarse — el issue del paquete no se reprodujo acá), la fila `tenants` y la base física desaparecieron juntas, verificado con una consulta fresca después, no solo por el mensaje de salida del comando. Segunda corrida contra un estado sin vencidos: no rompe, informa "nada que borrar".

**Todavía no está en el scheduler** (`routes/console.php`) — a diferencia de `subscriptions:reconcile` (REQ-3.6), que sí se agregó directo. Es una acción destructiva e irreversible corriendo sola todos los días sin supervisión — se deja el comando listo y probado, pero la decisión de activarlo en automático (`Schedule::command('tenants:prune-expired')->daily()`) se deja para cuando el usuario lo confirme explícitamente, no como parte de "implementar el REQ".

### 4.3 — Contexto B: asistido por staff, desde el Súper Admin (REQ-4.3)

**Revisado (2026-09-04) — ya no es "el mismo wizard, operado por otra persona".** El diseño original (`docs/features/v1.3.0.md`, versión previa a esta revisión) asumía que el Contexto B era el staff de ZertixPOS sentado con el cliente, llenando el mismo formulario público de `/install` en su nombre — "mismo flujo técnico, la única diferencia es quién lo opera". Al construir REQ-4.1/4.6 (el wizard real, con `Tenant` creado al final vía `ProvisionTenantJob` en cola) quedó claro que esa distinción no aporta nada real: si es el mismo formulario público, no hace falta ningún REQ aparte para "quién lo usa".

Esa revisión propuso entonces un **"Crear tenant"** aparte dentro del Panel de Súper Admin — un formulario propio, autenticado con el guard `landlord`, que solo reusara `ProvisionTenantJob` (no el componente `InstallWizard`). **Nunca se construyó** — quedó anotado como Pendiente hasta que existiera el panel (Fase 5) para alojarlo, y la tabla de requerimientos se marcó "Completada" por error del roadmap (no del código): no hay ningún trabajo real detrás, solo el análisis de esta sección.

**Segunda revisión (2026-09-14, al planear la Fase 5) — de vuelta a reusar el wizard, pero como enlace, no como formulario duplicado.** Construir un segundo formulario Admin/Empresa/Plan dentro del panel, aunque reuse `ProvisionTenantJob` por debajo, duplica exactamente los mismos pasos/validaciones/UI que `InstallWizard` ya tiene — sin ganar nada real a cambio, porque el motivo original para separarlo ("el staff no debe pasar por el formulario público") no es un problema técnico, es solo de flujo de pestaña. Decisión final: el botón **"Nuevo Tenant"** del listado (REQ-5.1) es un `<a href="{{ route('install.wizard') }}" target="_blank">` — abre `/install` (Contexto A, sin cambios) en una pestaña nueva. Dos razones por las que esto no rompe la separación landlord/staff que motivó la revisión anterior:

- **Nunca hay redirect automático a pisar la sesión del panel.** El paso Finalizar del wizard ya no hace `Auth::login()`/redirect real desde 2026-09-04 (ver 4.1, quinto hallazgo) — muestra un link real (`tenantLoginUrl`, botón "Entrar a mi negocio" + Copiar) que el usuario hace clic él mismo, precisamente para evitar el diálogo nativo de "¿salir del sitio?" de Chrome/Edge. Abrir el wizard en pestaña nueva hereda ese mismo comportamiento gratis: ese link, si se hace clic, navega la pestaña *del wizard*, nunca la pestaña del panel (`landlord`) — la sesión de Súper Admin queda intacta sin necesitar ningún cambio en `InstallWizard.php`.
- **No hay conflicto de guards.** `/install` corre en el dominio central sin middleware `auth` (nadie está logueado todavía, ver docblock de la ruta en `routes/web.php`) y no toca el guard `landlord` en ningún punto — es tenant-agnóstico, crea un `User` en la base del tenant *nuevo*, no en la conexión central. Abrirlo en una pestaña aparte de una sesión `landlord` activa en otra pestaña no interfiere con nada.

**Cero cambios de código en `InstallWizard.php`** — todo el trabajo de este REQ es el botón en la vista del panel (Fase 5) más, opcionalmente, una entrada al log/auditoría de qué admin del landlord disparó la creación (no construido, no bloqueante: el wizard ya registra el tenant igual sin saber quién lo abrió). Queda Pendiente hasta que exista el botón real.

### 4.4 — Tipo de negocio, antes del Plan (REQ-4.4)

**No es instalación de módulos a la carta, es curaduría de UX sobre lo que el Plan ya trae.** El Plan define el techo real de módulos disponibles (los trae todos, sin importar tipo de negocio) — tipo de negocio decide cuáles de esos módulos ya incluidos se muestran/activan en la UI de esa instalación puntual. Con Plan Pro, el módulo de Distribuidora existe en la instalación aunque el tipo de negocio sea "POS" — simplemente no se muestra si no aplica. Como tipo de negocio nunca puede activar algo que el Plan no incluye, un caso como "Distribuidora + Plan Básico" no es una contradicción bloqueante — como mucho, la UI lo muestra como sugerencia de upgrade.

Vive dentro del paso Empresa (no un 5to paso aparte), va **antes** del paso Plan para que este pueda **recomendar** el plan adecuado según lo que ese tipo de negocio suele necesitar — la reconciliación final siempre queda acotada por el Plan elegido. Sugiere un set de `installation_modules` por defecto según `modulos-base-satelite.md` (ej. "Colmado/Retail" → base mínimo, "Distribuidora con rutas" → suma satélite `Client→Equipment`), ajustable por el usuario.

### 4.6 — Paso Finalizar (REQ-4.6)

**"Finalizar" crea `Tenant`+`Domain`+`Subscription` (en `trialing`, ver REQ-3.8) y corre `tenants:migrate`/`seed`** — ya no depende de ningún cobro exitoso, es el efecto directo de completar el wizard.

**Hallazgo (2026-09-02): `InstallWizard::finish()` (`app/Livewire/Install/InstallWizard.php`) todavía es el instalador de un solo tenant de antes de Fase 1 — no implementa nada de esto.** Su ruta (`routes/web.php:12`, `Route::get('/install', InstallWizard::class)`) no lleva `InitializeTenancyByDomain`, así que corre siempre en contexto central/landlord, sin tenant inicializado. Hoy `finish()` nunca crea `Tenant`/`Domain`, y si se ejecutara contra una base landlord real fallaría en `User::create()` — `users` ya no existe en landlord, se movió a `database/migrations/tenant/` (REQ-1.7). Reescribir para REQ-4.6 es justamente resolver esto, no un ajuste menor.

**Mecanismo real (`$tenant->run()`), que resuelve la duda de "cómo sabe el seeder/`Plan::assignTo()` a qué base escribir":** `tenants:seed --tenants=<id>` es azúcar de CLI — internamente hace `$tenant->run(fn () => Artisan::call('db:seed', [...]))`. Lo único que importa es que la tenancy esté **inicializada** (con `database.default` swapeado al tenant) en el momento en que corre el seeder, no el nombre del comando. Un `Artisan::call('db:seed', ['--class' => 'DatabaseSeeder', '--force' => true])` corrido dentro de un `$tenant->run(function () { ... })` sí siembra contra la base del tenant, porque el swap de conexión aplica a todo el closure, en el mismo proceso PHP. Modelos con conexión fija (`Plan::$connection = 'landlord'`) ignoran ese swap y siguen escribiendo en landlord aunque el `DatabaseSeeder` completo (incluido `PlanSeeder`) corra adentro del mismo `run()` — así es como un solo método puede tocar las dos bases sin lógica especial en `Plan::assignTo()` ni en el seeder.

**Estructura propuesta para `finish()`:**

1. **En contexto central (fuera de `run()`):** crear `Tenant`+`Domain`, `Artisan::call('tenants:migrate', ['--tenants' => [$tenant->id]])` para ese tenant puntual, crear `Subscription` (`status='trialing'`, landlord — su propia conexión fija hace esto trivial desde cualquier contexto).
2. **Envuelto en un único `$tenant->run(function () use (...) { ... })`:** el `db:seed`, `User::create()`, `ConfiguracionGeneral::first()->update()`, y `Plan::findOrFail($this->planId)->assignTo()` — todo lo que hoy ya está en `finish()`, sin cambios de lógica interna, solo movido adentro del closure.
3. **Login y redirect no pueden ser `route('dashboard')`** — esa ruta vive en `routes/tenant.php`, inalcanzable desde contexto central. Hace falta un redirect cruzado de dominio hacia el subdominio recién creado, ya logueado contra la sesión de esa base tenant.
4. **Nota de rendimiento, no bloqueante:** `PlanSeeder`/otros pasos landlord de `DatabaseSeeder` se re-ejecutan en cada instalación de tenant nuevo (inofensivo porque son idempotentes, pero trabajo de más) — separar `DatabaseSeeder` en un seeder landlord y uno tenant es una mejora futura, no requisito de REQ-4.6.
5. **Caution de `stancl/tenancy`:** no devolver instancias de modelo Eloquent desde dentro de `$tenant->run()` hacia el contexto central que las llamó — su `$connection` queda apuntando a una conexión que ya no existe al salir del closure, lo que puede romper serializaciones posteriores (ej. Livewire). Si `finish()` necesita algo del tenant después del `run()`, devolver un array/ID, no el modelo.

### 4.7.1 — Cambio de plan y cancelación, desde la propia app (REQ-4.7.1)

**Por qué existe este REQ:** ninguna de las tres acciones (subir de plan, bajar de plan, cancelar) funciona bien hoy, y sin esto el Escenario C de REQ-4.8 (cancelación real) no tiene ninguna forma de dispararse desde ZertixPOS — solo cancelando a mano del lado de PayPal.

**El bug real de fondo:** `ManageSubscription::subscribe()` usa el mismo camino para "primera suscripción" y para "cambiar de plan" — `PaymentGatewayContract::createSubscription()`, que crea un acuerdo de PayPal **nuevo**, en paralelo al que ya existía. El viejo no se cancela solo. Resultado confirmado en el sandbox real: pasar de Plan PyME a Plan Pro cobró $59 y $89 por separado, dos suscripciones activas a la vez, no una migración de $59 a $89.

**Upgrade — sin prorrateo, efectivo en la próxima renovación (decisión de producto, no solo técnica).** PayPal no prorratea nada solo, y el precio nuevo recién aplica en el ciclo siguiente sin importar cuándo se apruebe — prorratear de verdad requeriría un cobro único aparte por fuera de la suscripción, calculado a mano. Para el público real de ZertixPOS (colmados, vendedores ambulantes, alguna empresa mediana — no un público que entienda "crédito prorrateado") se prefiere el camino simple: sin cobro doble, sin explicarle matemática de prorrateo a nadie. La pérdida de ingreso (el resto del ciclo actual "gratis" en el plan más caro) es chica y acotada, y más barata que una disputa de PayPal por un cobro que el cliente no esperaba.

**Corrección real sobre el plan original (confirmada en vivo contra el sandbox, no asumida):** un upgrade tampoco es instantáneo del todo — `reviseSubscription()` **siempre** devuelve un link de aprobación, upgrade o downgrade por igual (probado directo contra la API: el `plan_id` de PayPal no cambia hasta que el comprador completa esa aprobación). No hay forma de aplicar ningún cambio de plan "en silencio" — el comprador vuelve a pasar por una pantalla de PayPal, igual que al suscribirse la primera vez, aunque no haya ningún cobro de por medio. Las funcionalidades del plan nuevo se desbloquean apenas confirma ahí, no antes.

**Downgrade — se agenda, no se aplica ya.** Las funcionalidades del plan actual (ya pagado) siguen activas hasta `current_period_ends_at` — nunca se le apaga a alguien algo que ya pagó a mitad de ciclo. El cambio real (bajar `tenants.plan_id`, apagar los `installation_modules` que ya no correspondan) se aplica recién cuando el período efectivamente termina — el job de reconciliación diario que ya existe (REQ-3.6) es el lugar natural para aplicarlo, revisando si hay un cambio de plan agendado antes de solo marcar `past_due`. Antes de confirmar, hay que decirle al usuario explícitamente qué funcionalidades se apagan y en qué fecha — no alcanza con "vas a bajar de plan".

**Cancelación — mismo principio que el downgrade, y la mitad del trabajo ya existe.** `PayPalGateway::cancelSubscription()` ya cancela el cobro recurrente en PayPal de inmediato y ya deja `current_period_ends_at` intacto — como `EnsureSubscriptionActive` (REQ-3.5) solo bloquea por fecha, nunca por `status`, el acceso ya seguiría hasta el final del período pagado sin tocar nada de esa parte. Lo que falta es la conexión a la UI: no hay ningún botón/link en `ManageSubscription` que la llame. `billing.cancelled` (la vista que sí existe) no sirve para esto — es el destino del `cancel_url` de PayPal cuando alguien aborta el checkout antes de suscribirse, un caso completamente distinto.

**Diseño de la UI — mockup Stitch "Resumen de Suscripción: Cancelar Plan", adaptado a los componentes reales del proyecto, no calcado tal cual:**
- Link "Cancelar suscripción" (texto chico, `variant="error"`, `appearance="ghost"`, ver `docs/ui/buttons.md`) bajo el CTA principal de la tarjeta de plan actual, mismo lugar que el mockup.
- Modal de confirmación con `<x-modal>` (`resources/views/components/modal.blade.php`, patrón `$dispatch('open-modal', 'nombre')` / `x-on:open-modal.window`), **no** el modal armado a mano en JS puro del mockup (`document.getElementById(...).classList`) — mismo contenido, mecanismo real del proyecto.
- Adentro del modal, una caja de "consecuencias" explícita (qué sigue activo, hasta cuándo, que no se cobra de nuevo) — mismo espíritu que la caja de info del mockup, con datos reales de la `Subscription` (no texto fijo). El selector de motivo de cancelación (radios + comentario opcional) del mockup es opcional, no bloqueante para esta primera versión — es útil para el negocio pero no es lo que arregla el bug real.
- Dos acciones al pie: mantener la suscripción (cierra el modal, `x-ui.button` `variant="primary"`) y confirmar cancelación (`variant="error"`, `appearance="outline"` en vez de `solid` — coherente con que es una acción destructiva pero no irreversible-inmediata, ya que el acceso sigue activo hasta el fin del período).

**Implementado.**

- **`subscriptions.scheduled_plan_id`** (migración nueva, sin FK — mismo criterio que `plan_id`, que tampoco la tiene) — el plan al que `tenants.plan_id` baja cuando `current_period_ends_at` termine. `Subscription::scheduledPlan()` como relación de conveniencia.
- **`PaymentGatewayContract::reviseSubscription()`** — nuevo en el contrato. `PayPalGateway` lo implementa llamando al `reviseSubscription()` del paquete `srmklive/paypal` (ya existía, sin usar) con `application_context.return_url`/`cancel_url` — mismo patrón que `createSubscription()`, probado en vivo que el endpoint `revise` los acepta.
- **`PayPalGateway::activate()` reescrito como la pieza central del REQ** — antes asumía que el `plan_id` local ya era el correcto; ahora lo resuelve SIEMPRE desde lo que PayPal reporta (`resource.plan_id` → `Plan::where('gateway_plan_id', ...)`), así que sirve tanto para una activación inicial como para la vuelta de una revisión de plan. Compara el plan resuelto contra el plan que el tenant tiene activo AHORA (no contra el que la fila de `Subscription` tenía guardado) para decidir upgrade vs. downgrade: si cuesta igual o más, `tenants.plan_id` se mueve ya; si cuesta menos, se guarda en `scheduled_plan_id` sin tocar `tenants.plan_id`. Un upgrade posterior cancela cualquier downgrade agendado previo.
- **`syncSubscriptionStatus()` perdió su atajo "ya está `active`, no hago nada"** — ese atajo (necesario antes de este REQ) rompía el retorno de un `reviseSubscription()`: una suscripción activa que vuelve de cambiar de plan sigue activa de principio a fin, así que el atajo se saltaba `activate()` entero y el cambio nunca se reflejaba. Ahora siempre pregunta a la API.
- **`ManageSubscription`** — `subscribe()` ahora rama entre `createSubscription()` (primera vez) y `reviseSubscription()` (`isChangeOfPlan`, hay un acuerdo de PayPal ya activo) sin duplicar la pantalla de checkout; el checkout muestra un aviso de "no se te cobra nada hoy" en vez del desglose de precio cuando es cambio de plan. `openCancelModal()`/`confirmCancel()` nuevos, conectan el modal a `cancelSubscription()` (ya existía, nunca tenía quién la llamara).
- **`ReconcileSubscriptions` (REQ-3.6) extendido** — `applyScheduledDowngrades()`, corre antes de marcar `past_due`. Es el único lugar del sistema que aplica un cambio de plan en contexto de tenant real (`Tenant::run()` + `Plan::assignTo()`), así que además de mover `tenants.plan_id` re-provisiona `installation_modules` correctamente — cierra la limitación conocida que el camino del webhook (contexto central puro) sigue teniendo, documentada en REQ-3.11.
- **Verificado con la lógica real, sin mockear nada:** `activate()` invocado directo (por reflexión, mismo criterio que otras verificaciones de esta fase) simulando la respuesta de PayPal para un downgrade (Pro→Emprendedor) y un upgrade (PyME→Pro) sobre una suscripción real del sandbox — el downgrade dejó `tenants.plan_id` intacto y agendó `scheduled_plan_id`; el upgrade movió `tenants.plan_id` al instante. Corrido `subscriptions:reconcile` con `current_period_ends_at` forzado al pasado — `tenants.plan_id` bajó al plan agendado y `installation_modules` se re-provisionó de verdad (`sales.delivery_points`/`clients.field_assets` — exclusivos de Pro — quedaron en `false` tras bajar a Emprendedor).

**Tres bugs reales, encontrados por el usuario probando el flujo en vivo (moviendo fechas y corriendo `subscriptions:reconcile` a mano), no por revisión de código. Corregidos y verificados en vivo (2026-09-09):**

1. **Suscripciones `pending` duplicadas — y, encontrado después, acuerdos de PayPal huérfanos y activos por el mismo motivo.** `ManageSubscription::subscribe()` creaba una fila `Subscription` nueva en cada llamada, sin limpiar intentos abandonados — ir "Atrás" en el navegador después de ser redirigido a PayPal y volver a tocar "Pagar" acumulaba una fila `pending` más por intento. El primer fix asumía "nunca se aprobó, no hay nada real que perder" y solo borraba la fila local (`delete()`) — **falso en la práctica**: probando de punta a punta (2026-09-12) se encontraron, del lado real de PayPal (cuenta business del sandbox, listado de suscripciones del vendedor), **5 acuerdos `ACTIVE` de verdad sin ninguna fila local que los rastreara** — uno de ellos con el `custom_id` de un tenant real, cobrando en segundo plano, invisible para el resto de la app (nunca se factura, nunca se puede cancelar desde acá). Un segundo caso del mismo problema apareció renovando tras `past_due` (punto 2 de abajo): el acuerdo VIEJO nunca se cancelaba al crear el nuevo, y ambos quedaban `ACTIVE` en PayPal en paralelo. Fix definitivo, generalizado: antes de `createSubscription()`, cualquier suscripción previa del tenant con un acuerdo real (`gateway_subscription_id`) que no esté ya `cancelled` —sea `pending`, `past_due`, lo que sea— se cancela primero del lado de PayPal (mejor esfuerzo) y recién después se crea la nueva. Nunca deben convivir dos acuerdos reales vivos para el mismo tenant. Los 5 acuerdos huérfanos encontrados se cancelaron a mano tras confirmar que ninguno correspondía a algo que debiera seguir cobrando.
2. **No se podía renovar seleccionando el mismo plan ya vencido.** `selectPlan()` bloqueaba re-seleccionar el plan actual sin importar el estado de la suscripción — pero un `past_due`/`cancelled` necesita un acuerdo de PayPal genuinamente nuevo (`createSubscription()`, el único camino que dispara un cobro real) para "renovar", sea el mismo plan o no; `reviseSubscription()` nunca cobra nada, solo cambia el plan para el ciclo siguiente. El guard de `selectPlan()` y `getIsChangeOfPlanProperty()` ahora solo tratan una suscripción como "cambio de plan sobre un acuerdo vivo" cuando `status` es `active`/`trialing` — cualquier `past_due`/`cancelled` siempre pasa por `createSubscription()`, sin importar el plan elegido. **La vista tenía el mismo bug por otro lado:** la tarjeta del plan actual en "Elegí tu plan" mostraba el botón "Plan actual" deshabilitado sin importar el estado — corregido para que, cuando la suscripción no está viva (`past_due`/`cancelled`), esa misma tarjeta muestre "Renovar este plan" y dispare `selectPlan()` igual que cualquier otra.
3. **Se intentó "detectar" renovaciones automáticas sin webhook — descartado por decisión explícita del usuario, no es un fix que haya quedado.** Un primer intento (`ReconcileSubscriptions::syncNearRenewals()` + `PayPalGateway::recordPaymentIfAny()`) le preguntaba proactivamente a la API si la suscripción seguía `ACTIVE` y, de ser así, la trataba como renovada — pero **`ACTIVE` no prueba que hubo un cobro nuevo**, y se confirmó en vivo un caso real donde `billing_info.last_payment` de una suscripción recién creada (`cycles_completed: 0`, ningún ciclo real completado todavía) devolvía el monto de una suscripción *anterior* del mismo comprador sandbox — habría generado una factura con el monto equivocado, atribuida a la suscripción equivocada. Se revirtió por completo: `ReconcileSubscriptions` volvió a ser solo "marcar `past_due` + aplicar downgrades agendados", y `SubscriptionInvoice` vuelve a crearse **únicamente** desde el webhook real (`onPaymentCompleted()`, `PAYMENT.SALE.COMPLETED`) — el único evento que trae un id de transacción único y un monto verificado, sin ambigüedad. **Decisión de producto explícita:** no hay auto-renovación confiable posible sin depender del webhook (que ya probó fallar), así que se abandona la idea — cuando una suscripción vence, el cliente paga de nuevo desde la app en ese momento (mismo flujo que suscribirse la primera vez, ver punto 2), en vez de esperar a que PayPal la renueve solo en segundo plano.

**Sobre `cloudflared` vs. `ngrok` para el webhook — causa real encontrada (2026-09-12), corrige un diagnóstico anterior equivocado.** El análisis previo (ver REQ-3.11 más arriba) concluyó "PayPal nunca intenta entregar el evento" a partir de un `curl` directo que sí llegaba pero de ningún rastro de un intento real de PayPal en los logs. Esa conclusión era incompleta: la URL de webhook registrada en el Developer Dashboard de PayPal (`PAYPAL_WEBHOOK_ID`) apuntaba a un túnel de `cloudflared` que ya no existía desde hacía días — PayPal sí intentaba entregar, pero contra una URL muerta, sin ningún error visible del lado de la app porque la entrega ni siquiera llegaba a la red local. Se instaló `ngrok`, se actualizó la URL del webhook vía la API de PayPal (`PATCH /v1/notifications/webhooks/{id}`) apuntando al túnel nuevo, y **el webhook llegó de verdad** en cada prueba posterior — activación, downgrade, cancelación y renovación, todas con su evento real recibido y procesado. Conclusión corregida: el webhook de PayPal **si funciona** con una URL pública viva y registrada correctamente; el problema nunca fue de confiabilidad de PayPal ni de qué túnel usar. La arquitectura de REQ-3.11 (confirmar el pago inicial y cualquier cambio de plan de forma síncrona al volver de PayPal, sin esperar el webhook) se mantiene igual — es la más robusta ante una eventual caída del webhook — pero la factura de una renovación real sí depende de que el webhook llegue (punto 3 arriba: se decidió no auto-detectar renovaciones sin él), así que en producción es indispensable mantener la URL del webhook viva y apuntando al dominio real, no a un túnel temporal.

**Sobre enviar la factura por correo / instalar Mailpit (pregunta del usuario):** no existe hoy ningún `Mailable`/`Notification` para facturas en `app/Mail`/`app/Notifications`, `MAIL_MAILER=log`, y no hay servicio de Mailpit en `docker-compose.yaml`. Es una funcionalidad real y esperable de cualquier billing, pero es un deliverable nuevo (plantilla de correo + envío en el punto donde se crea el `SubscriptionInvoice`), no parte de arreglar estos bugs — queda fuera de REQ-4.7.1 a propósito, para no mezclar corrección de bugs con una funcionalidad nueva. Instalar Mailpit sí es barato y útil en general para desarrollo local (cualquier correo futuro, no solo facturas) — recomendado como tarea aparte, pequeña, cuando haga falta probar envíos reales.

**Un cuarto bug real, encontrado recién con el webhook funcionando de verdad (2026-09-12): un tenant en trial que paga por primera vez quedaba mal clasificado como "downgrade".** `PayPalGateway::activate()` decide upgrade/downgrade comparando el plan nuevo contra `tenants.plan_id` — pero ese campo existe desde el Wizard aunque nunca se haya pagado nada (el trial asigna un plan gratis, a veces uno caro, como señuelo). Un tenant en trial de Pro que pagaba por primera vez un plan más barato (PyME) quedaba con `tenants.plan_id` frizado en Pro (nunca pagado) y el plan realmente pagado agendado para dentro de un mes — en pantalla: pagó $62.68 y la app le mostraba "Plan Actual: Pro, $89/mes". Dos rondas de corrección, ambas verificadas por reflexión sobre una suscripción real del sandbox:
- **Primera corrección:** agregar un chequeo `$hadPriorRealSubscription` — solo es downgrade si YA existía otra fila de `Subscription` del tenant con un acuerdo real de PayPal antes de esta. Corrigió el caso trial→pago, pero…
- **Segunda corrección (encontrada probando el downgrade real de punta a punta):** un cambio de plan de verdad (`reviseSubscription()`) reutiliza la MISMA fila, nunca crea una nueva — con el chequeo de "otra fila", un downgrade real sobre una suscripción activa se aplicaba de inmediato en vez de agendarse (el bug inverso al original). ### 4.9 — Correo de factura al confirmarse un pago (REQ-4.9)

**Por qué ahora, y por qué así:** con `SubscriptionInvoice` ya creándose de forma confiable (REQ-4.7.1/4.8), faltaba la última pieza esperable de cualquier billing — avisarle al cliente que se le cobró, con algo que pueda guardar. Mismo patrón que Stripe/Claude: el cuerpo del correo trae el resumen (monto, plan, fecha, método) y un botón "Ver factura (PDF)" que **linkea**, no adjunta — un adjunto pesa por mensaje y algunos proveedores SMTP transaccionales cobran o limitan por tamaño de adjunto; un link no pesa nada, y el PDF se genera al vuelo con el diseño vigente, no con el de cuando se envió el correo.

**Implementado:**
- **`app/Mail/Billing/InvoicePaid.php`** — `Mailable implements ShouldQueue` (no debe hacer esperar la respuesta al webhook de PayPal por un envío lento). El link del PDF es una `URL::temporarySignedRoute()` (30 días de vigencia) — no depende de que el cliente tenga sesión iniciada, la firma de Laravel es suficiente para que nadie adivine la URL de la factura de otro.
- **`app/Http/Controllers/Billing/InvoicePdfController.php`** + ruta `GET /facturas/{invoice}/pdf` (`routes/web.php`, central — `SubscriptionInvoice` es landlord, mismo motivo que el webhook) — genera el PDF al vuelo con `barryvdh/laravel-dompdf` (ya usado en el resto del sistema, `InvoicePrintService`), no lo guarda en disco. Protegida por el middleware `signed`, sin `auth`.
- **Disparo único: `PayPalGateway::onPaymentCompleted()`** — el mismo y único punto donde ya se crea el `SubscriptionInvoice` real (webhook `PAYMENT.SALE.COMPLETED`). El destinatario se resuelve entrando en contexto de tenant (`Tenant::run()`, mismo patrón que `ReconcileSubscriptions::applyScheduledDowngrades()`) porque `User` es un modelo por-tenant — se le manda al usuario con el rol protegido (`admin`), la única cuenta que siempre existe sin depender de a quién le tocó pagar.
- **Bug real encontrado armando esto: `subscription_invoices` no sabía qué plan se pagó, solo lo derivaba de `subscription->plan_id` (mutable) — una factura vieja de PyME se mostraba como "Plan Pro" después de un upgrade posterior**, porque el join seguía al plan ACTUAL de la suscripción, no al vigente el día del pago. Una factura es un registro histórico, no debe cambiar retroactivamente por acciones futuras. Fix: migración `add_plan_id_to_subscription_invoices_table` (sin FK, mismo criterio que `subscriptions.plan_id`) — `onPaymentCompleted()` graba `$subscription->plan_id` en el momento exacto del cobro; `SubscriptionInvoice::plan()` relación nueva, con fallback a `subscription->plan` para las 3 facturas reales creadas antes de este fix (backfilleadas a mano con el plan real que pagaron en su momento).
- **Mailpit agregado a `docker-compose.yaml`** (imagen `axllent/mailpit`, puertos 1025/SMTP y 8025/dashboard web) — `.env`/`.env.example` cambian `MAIL_MAILER=log` → `smtp`/`mailpit`/`1025`, para poder ver los correos reales en desarrollo local sin depender de ningún proveedor externo.
- **Worker de cola agregado como servicio propio (`queue`, `docker-compose.yaml`)** — hallazgo real: el `Dockerfile` de Sail nunca corrió ningún `queue:work`/`queue:listen` (`supervisord.conf` solo arranca PHP-FPM), así que cualquier `ShouldQueue` de este proyecto se quedaba encolado para siempre en este entorno sin que nadie lo notara. El servicio nuevo reusa la misma imagen (`sail-8.4/app`) con `command: queue:work`, dejando que el propio `start-container` de la imagen lo corra como el usuario `sail` (vía `gosu`), no como root — mismo cuidado que ya pide `CLAUDE.md` para no dejar archivos compilados con dueño incorrecto.
- **Verificado en vivo, de punta a punta, sin mockear nada:** pago real completo en el navegador (PayPal Sandbox) → webhook real recibido → `SubscriptionInvoice` creada con el `plan_id` correcto → correo encolado automáticamente (sin intervención manual) → **worker persistente lo procesó solo** → confirmado en la bandeja real de Mailpit (asunto, monto y plan correctos) → link firmado del correo abierto por `curl`, `Content-Type: application/pdf`, PDF válido de una página con los datos correctos.

### 7.6 — Perfil de Usuario: migración real, no solo cosmética (REQ-7.6)

**Confirmado en código, no es una impresión.** `resources/views/profile/edit.blade.php` y sus 3 partials eran el scaffolding de Laravel Breeze **sin ningún cambio** desde que se instaló el proyecto — títulos y textos en inglés ("Profile Information", "Update your account's profile information...", "Delete Account"), componentes de Breeze (`x-input-label`, `x-text-input`, `x-primary-button`) en vez de `x-ui.forms.*`/`x-ui.button` que ya usa el resto del sistema, sin avatar, sin mostrar el rol del usuario. Se migró al diseño del mockup de Stitch ("Perfil de Usuario - ZertixPOS"): header con avatar de iniciales + chip de rol, y dos tabs por ahora (Datos Personales/Seguridad) — Preferencias y Actividad, que el mockup trae pero sin nada real detrás todavía, quedan fuera de esta pasada.

**Hallazgo aparte, de seguridad/diseño de producto, no solo de estilo:** `delete-user-form.blade.php` era el formulario de auto-borrado de cuenta de Breeze, intacto — cualquier usuario logueado (un cajero, cualquiera) podía eliminar su propia cuenta permanentemente, sin pasar por un administrador. Eso tiene sentido en una app SaaS genérica de un solo usuario por cuenta, pero no en ZertixPOS: las cuentas de un negocio las crea y gestiona el dueño/admin desde el módulo de Usuarios (ver REQ-2.7), un empleado no debería poder borrarse a sí mismo del sistema por su cuenta. Al migrar, este botón se eliminó del perfil junto con `ProfileController::destroy()` y la ruta `profile.destroy` — el borrado de una cuenta sigue existiendo, pero solo como acción del admin desde Usuarios, nunca auto-servicio.

**Construido y verificado de punta a punta (2026-09-18).** `resources/views/profile/index.blade.php` reemplaza `edit.blade.php` — header (avatar de iniciales, nombre, correo, badge de rol vía `x-ui.badge`) + nav de 2 tabs con `x-data="{ tab: 'personal' }"` de Alpine (sin Livewire, no hace falta acá) + `@include` de `profile.partials.tab-personal-data`/`tab-security`, tal como pidió el usuario. Solo campos reales de `users` (`name`/`email`) — sin teléfono ni "Cambiar Foto" del mockup, esas columnas no existen en la tabla y no se inventaron. "Rol del Sistema" se muestra de solo lectura (`x-ui.forms.input disabled`, ícono de candado). El guard de cuenta demo (`tenant()->is_demo`, REQ-3.9) ya existía server-side en los dos `FormRequest` — se reflejó también en la UI: el campo de correo queda `disabled` y la pestaña de Seguridad muestra un aviso en vez del formulario, para no dejar que el usuario llene todo y recién se entere al enviar.

**Hallazgo real al construir la tarjeta "Sesión Actual" del mockup:** este proyecto usa `SESSION_DRIVER=redis` (`.env`) — la tabla `sessions` que Breeze trae de fábrica nunca se llena, así que un primer intento de leer "iniciada hace X" de ahí siempre devolvía vacío. Se resolvió mostrando solo la IP real del request actual (`$request->ip()`), el único dato de sesión que es cierto sin importar el driver.

Probado en el navegador real: con una cuenta del tenant `demo` (correo bloqueado, tab de Seguridad reemplazado por el aviso) y con un usuario de prueba en un tenant real sin restricción — cambio de nombre guardado y reflejado en el header tras el redirect, y cambio de contraseña confirmado directo contra el hash en base de datos antes de borrar el usuario de prueba.

### 7.9 — Fix CSS: `x-ui.forms.*` en estado de error (extra, sin REQ propio)

**Reportado con captura real** de `resources/views/profile/partials/tab-security.blade.php` (cambiar contraseña con la actual incorrecta). Dos bugs de UX en el mismo flujo, ambos confirmados en el código antes de tocar nada:

1. **El ícono de error tapaba el toggle de mostrar/ocultar contraseña.** `input.blade.php` decidía el ícono derecho con `@if ($error) ... @elseif ($isPassword())` — mutuamente excluyente, así que con ambos verdaderos el botón del ojito no se renderizaba. El usuario perdía la única forma de revisar qué escribió mal justo cuando más lo necesitaba. Confirmado además que esto no era un accidente: `docs/ui/forms.md` documentaba esa prioridad como comportamiento intencional. Se invirtió el orden (`isPassword()` primero) — el error se sigue viendo igual (borde/fondo rojo + mensaje debajo), y el propio botón ya se pinta de `text-state-error` vía `iconColorClasses()` cuando hay error.
2. **El borde/ring rojo se reafirmaba al hacer foco en vez de neutralizarse.** `inputClasses()`/`selectClasses()`/`textareaClasses()`/`groupWrapperClasses()` definían `focus:border-state-error`/`focus-within:border-state-error` en el branch de error — el propio foco reforzaba el rojo. Como el error es un string ya resuelto por Blade (`$errors->first(...)` o una prop Livewire), no hay forma de saber "el usuario tiene el campo enfocado ahora" sin JS. Se agregó, solo cuando hay `error`, un estado Alpine `focused` (`x-data`, listeners `@focus`/`@blur`) que aplica clases `!` (`!important`) para neutralizar el rojo mientras dura el foco — mismo look que un campo sin error en foco normal. El ícono izquierdo y el mensaje de error se quedan en rojo a propósito (referencia de qué se está corrigiendo); solo el marco/fondo del campo se neutraliza.

**Verificado sin navegador real** (el tenant `demo` bloquea el cambio de contraseña por diseño, REQ-7.6 — no se pudo reproducir el flujo completo en vivo): renderizado directo de `<x-ui.forms.input>`/`<x-ui.forms.select>`/`<x-ui.forms.textarea>` vía `Blade::render()` en `tinker` con `type="password"` + `error` simultáneos, confirmando que el toggle se renderiza (no el ícono de error) y que las clases `focused ? '!border-zertix-primary ...' : ''` quedan correctamente emitidas. Se compiló Tailwind contra el código real (`npx tailwindcss --content './resources/views/**/*.blade.php'`) y se confirmó que las 6 clases `!important` nuevas (`!border-zertix-primary`, `!ring-zertix-primary/20`, `!bg-white`, `!text-slate-600`, `!text-slate-800`, `!ring-1`) sí las detecta el scanner y las compila.

**Archivos tocados:** `app/View/Components/Ui/Forms/Input.php` (nuevo método `alpineData()`), `resources/views/components/ui/forms/input.blade.php`, `select.blade.php`, `textarea.blade.php`, más `docs/ui/forms.md` (documentado el comportamiento nuevo). `Checkbox`/`Radio`/`Toggle`/`FileInput` no comparten el patrón de borde/ring en foco (o no tienen `type="password"`), quedan fuera de este fix.
