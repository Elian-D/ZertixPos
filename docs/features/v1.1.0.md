# ZertixPOS v1.1.0 — Desacoplamiento de Contabilidad y Arquitectura de Módulos Base/Satélite

**RAMA PADRE:** `feature/v1.1.0-modular-architecture`

**Objetivo:** Terminar la deuda de alcance documentada en `docs/analisis/sobre-ingenieria-modulos.md` y `docs/analisis/modulos-base-satelite.md`: desacoplar el motor de Contabilidad de las 11 llamadas automáticas que hoy lo hacen un punto único de falla, construir la infraestructura genérica de módulos base/satélite (registro, flags por instalación, middleware con 404 en rutas no autorizadas), consolidar NCF dentro de ese mismo sistema, introducir el modelo de `Plan` como plantilla reutilizable de flags, reorganizar la estructura de rutas administrativas y de Configuración General, depurar los datos geográficos a solo RD, separar los seeders de desarrollo de los de producción, y construir los dos wizards que ponen todo esto en manos de un cliente real: el Wizard de Instalación (primer arranque, técnico) y el Wizard de Completar Instalación (backoffice, lo corre el dueño del negocio).

> **Alcance explícito:** esta versión sienta las bases para el futuro multi-tenant (`stancl/tenancy`, documentado como fase SaaS en `docs/promts.md`) sin construirlo — cada cliente sigue siendo una instalación aislada en su propio subdominio, instalada a mano por el equipo. El diseño de `Plan`/`installation_modules`, la organización de rutas (`admin/` como prefijo separable de un futuro `superadmin/`), y el wizard de completar instalación están pensados para reutilizarse 1:1 cuando llegue el multi-tenant, sin rediseño.

> **La partida doble no es prioridad en esta versión.** Contabilidad formal (`AccountingAccount`/`JournalEntry`) se desacopla y se apaga por defecto — no se invierte en hacerla mejor, solo en que dejar de usarla no rompa nada. Lo que sí es prioridad: que cualquier instalación pueda ver sus ganancias y gastos usando `Sale`, `InventoryMovement` y `Payment`/CxC, sin necesitar un solo asiento contable.

## Fase 1 — Reorganización de Rutas Administrativas (REQ-01)
**Rama:** `feature/v1.1.0-routes-cleanup`

### Por qué va primero

Las Fases 2 a 4 agregan middleware (`module:...`) a grupos de rutas existentes. Si la reorganización de archivos se hace después, ese trabajo de middleware hay que rehacerlo en la nueva ubicación — más barato reorganizar primero y que todo lo demás se escriba directo sobre la estructura final. Es **puramente estructural**: nombres de ruta, prefijos, middleware existente y controladores no cambian, solo dónde vive cada `Route::` físicamente.

### 1.1 — Eliminar `RouteServiceProvider`

```php
// ANTES — app/Providers/RouteServiceProvider.php
public function boot(): void
{
    Route::middleware('web')->group(base_path('routes/web.php'));

    Route::middleware(['web', 'auth'])
        ->prefix('admin')
        ->group(function () {
            foreach (glob(base_path('routes/admin/*.php')) as $routeFile) {
                require $routeFile;
            }
        });
}
```

Esta clase se elimina del `config/app.php` (providers) y del archivo. Su lógica se mueve completa a `routes/web.php`:

```php
// routes/web.php — al final, reemplaza lo que hacía el provider

Route::get('/', function () {
    return view('welcome');
});

Route::get('/dashboard', function () {
    return view('dashboard');
})->middleware(['auth', 'verified', 'permission:view dashboard'])->name('dashboard');

Route::middleware('auth')->group(function () {
    Route::get('/profile', [ProfileController::class, 'edit'])->name('profile.edit');
    Route::patch('/profile', [ProfileController::class, 'update'])->name('profile.update');
    Route::delete('/profile', [ProfileController::class, 'destroy'])->name('profile.destroy');
});

require __DIR__.'/auth.php';

// Rutas administrativas (panel) — antes vivía en RouteServiceProvider::boot()
Route::middleware(['web', 'auth'])
    ->prefix('admin')
    ->group(function () {
        foreach (glob(base_path('routes/admin/*.php')) as $routeFile) {
            require $routeFile;
        }
    });
```

## Fase 2 — Desacoplar Contabilidad y Simplificar `DocumentType` (REQ-02)
**Rama:** `feature/v1.1.0-accounting-decouple`

### Estrategia

Ningún cambio de comportamiento visible todavía — el objetivo es que el plan de cuentas deje de ser peligroso de editar, y que `DocumentType` deje de aparentar ser más de lo que es.

### 2.1 — Mapeo configurable de cuentas (REQ-02.1)

```php
// database/migrations/xxxx_create_accounting_account_roles_table.php

Schema::create('accounting_account_roles', function (Blueprint $table) {
    $table->id();
    $table->string('role')->unique(); // 'cash_default', 'receivable_default', 'sales_revenue', ...
    $table->foreignId('accounting_account_id')->constrained('accounting_accounts');
    $table->timestamps();
});
```

```php
// app/Models/Accounting/AccountingAccountRole.php

class AccountingAccountRole extends Model
{
    protected $fillable = ['role', 'accounting_account_id'];

    public static function resolve(string $role): ?int
    {
        return Cache::rememberForever("accounting_role_{$role}", function () use ($role) {
            return static::where('role', $role)->value('accounting_account_id');
        });
    }
}
```

### 2.2 — Reemplazar los 5 puntos de código hardcodeados (REQ-02.2)

`SaleService`, `InventoryMovementService` — prioridad más alta, corre en cada movimiento de stock —, `ReceivableService`, `PaymentService`, `AccountingDashboardController`:

```php
// ANTES

// DESPUÉS
```

### 2.7 — Correlativo editable solo si el negocio nunca facturó con ese tipo (REQ-02.7)

**El catálogo de Tipos de Documento pasa a ser, en la práctica, solo para ver y ajustar el correlativo** — un nice-to-have para que el negocio pueda igualar el número inicial con sus talonarios físicos, no una obligación. La regla: si ya existe al menos una `Sale` (o `Payment`, según el tipo) usando ese `document_type_id`, `current_number` deja de ser editable — ni hacia adelante ni hacia atrás. Cambiarlo después de la primera venta real rompería la integridad de los NCF ya emitidos y la trazabilidad contable.

```php
// app/Http/Requests/Accounting/DocumentTypes/UpdateDocumentTypeRequest.php

public function withValidator($validator): void
{
    $validator->after(function ($validator) {
        $type = $this->route('document_type');
        $changingNumber = $this->filled('current_number')
            && (int) $this->current_number !== $type->current_number;

        if ($changingNumber && $this->hasIssuedDocuments($type)) {
            $validator->errors()->add(
                'current_number',
                'No se puede modificar el correlativo: ya existen documentos emitidos con este tipo. Cambiarlo comprometería la integridad de la numeración y los NCF ya emitidos.'
            );
        }
    });
}

private function hasIssuedDocuments(DocumentType $type): bool
{
    return match ($type->code) {
        'FAC' => Sale::where('document_type_id', $type->id)->exists(),
        'PAG' => Payment::where('document_type_id', $type->id)->exists(), // si Payment guarda esta FK
        default => false, // futuros tipos: siempre editable
    };
}
```

**Verificación:** con el seeder de roles corrido, crear una venta debe seguir generando el mismo asiento que antes. Intentar cambiar el correlativo de `FAC` después de esa venta debe rechazarse con el mensaje de validación; en una instalación fresca sin ventas, el correlativo de `FAC` debe poder editarse libremente.

### 2.8 — Separar abono operativo de asiento contable en `PaymentService` (REQ-02.8)

Confirmado contra código real (ver `docs/analisis/modulos-base-satelite.md`): hoy `PaymentService::createPayment()` fuerza un `JournalEntry` completo y `AccountingAccount::where('code','1.1.01')` hardcodeado solo para poder registrar un abono. Eso es exactamente lo que rompe CxC si `accounting.advanced` se apaga — se corrige separando el método en dos pasos independientes.

```php
// app/Services/Accounting/Payment/PaymentService.php

public function createPayment(array $data): Payment
{
    return DB::transaction(function () use ($data) {
        $receivable = Receivable::findOrFail($data['receivable_id']);

        // 1. Abono operativo — corre SIEMPRE, sin depender de accounting.advanced
        $payment = Payment::create([
            'client_id'      => $receivable->client_id,
            'receivable_id'  => $receivable->id,
            'tipo_pago_id'   => $data['tipo_pago_id'],
            'amount'         => $data['amount'],
            'payment_date'   => $data['payment_date'],
            'reference'      => $data['reference'] ?? null,
            'note'           => $data['note'] ?? null,
            'created_by'     => Auth::id(),
            'status'         => Payment::STATUS_ACTIVE,
        ]);

        $receivable->current_balance -= $data['amount'];
        $this->receivableService->updateStatusBasedOnBalance($receivable);
        $receivable->client->refreshBalance();

        // 2. Asiento contable derivado — SOLO si accounting.advanced está activo
        if (module_enabled('accounting.advanced')) {
            $entry = $this->journalService->create([
                'entry_date'  => $data['payment_date'],
                'description' => "Pago Recibido — Cliente: {$receivable->client->name}",
                'status'      => JournalEntry::STATUS_POSTED,
                'items'       => [
                    ['accounting_account_id' => AccountingAccountRole::resolve('cash_default'), 'debit' => $data['amount'], 'credit' => 0],
                    ['accounting_account_id' => $receivable->accounting_account_id, 'debit' => 0, 'credit' => $data['amount']],
                ],
            ]);

            $payment->update(['journal_entry_id' => $entry->id]);
        }

        return $payment;
    });
}
```

El `receipt_number`/`DocumentType::where('code','PAG')` (correlativo formal) también queda condicionado al mismo flag — sin `accounting.advanced`, el abono se registra sin número de recibo formal, solo con el registro operativo. `cancelPayment()` recibe el mismo tratamiento simétrico: revertir el asiento solo si existe.

**Verificación:** con `accounting.advanced` en `false`, registrar un abono a una `Receivable` debe actualizar `current_balance` y el estado (`unpaid`/`partial`/`paid`) sin crear ningún `JournalEntry` ni requerir que existan cuentas contables sembradas.     $table->string('name');
```php
    $table->string('slug')->unique();
    $table->text('description')->nullable();
    $table->timestamps();

Schema::create('plan_module', function (Blueprint $table) {
    $table->foreignId('plan_id')->constrained()->cascadeOnDelete();
```

### 5.2 — Modelo y asignación (copia explícita, no join en vivo)

```php
class Plan extends Model
{
    protected $fillable = ['name', 'slug', 'description'];

    public function moduleKeys(): array
    {
        return DB::table('plan_module')->where('plan_id', $this->id)->pluck('module_key')->all();
    }

    public function assignTo(): void
    {
        $moduleKeys = $this->moduleKeys();

        collect(config('modules'))->keys()->each(function (string $key) use ($moduleKeys) {
            InstallationModule::updateOrCreate(
                ['module_key' => $key],
                ['is_enabled' => in_array($key, $moduleKeys, true)]
            );
        });
    }
}
```

## Fase 6 — Depuración Geográfica (REQ-06)
**Rama:** `feature/v1.1.0-geo-rd-only`

### Estrategia

Un dump SQL limpio (`geo_data_rd.sql`) con solo países/estados de RD, sin distritos ni barrios (confirmado sin uso real en ningún flujo). La importación **no usa `exec()` con el binario `mysql`** — depender de que `mysql` esté en el `PATH` del sistema es exactamente el tipo de cosa que funciona distinto en Sail (contenedor Linux) y en Laragon (Windows, MySQL empaquetado aparte, `PATH` no siempre configurado). Se usa `DB::unprepared()`, que va por la misma conexión PDO que ya usa toda la app — funciona igual en cualquier entorno donde Laravel ya corre, sin binarios externos.

### 6.1 — El dump

`database/seeders/sql/geo_data_rd.sql` — solo `INSERT` de `countries`/`states` para República Dominicana, sin las tablas de distrito/barrio (se depuran del dump, no solo se dejan de usar).

### 6.2 — Seeder portable

```php
// database/seeders/AppInit/GeoDataSeeder.php

namespace Database\Seeders\AppInit;

use Illuminate\Database\Seeder;
use Illuminate\Support\Facades\DB;

class GeoDataSeeder extends Seeder
{
    public function run(): void
    {
        $path = database_path('seeders/sql/geo_data_rd.sql');

        if (!file_exists($path)) {
            $this->command?->warn("geo_data_rd.sql no encontrado en {$path}, se omite.");
            return;
        }

        // DB::unprepared() ejecuta el SQL crudo por la conexión PDO ya configurada
        // en config/database.php — no depende de un binario `mysql` en el PATH del
        // sistema operativo, así que funciona igual en Sail (Linux) y en Laragon
        // (Windows) sin configuración adicional. Solo apto para dumps de solo
        // INSERT/CREATE simples, sin DELIMITER de procedimientos almacenados
        // (que no es el caso de un dump de países/estados).
        DB::unprepared(file_get_contents($path));

        $this->command?->info('Datos geográficos de RD importados correctamente.');
    }
}
```

### 6.3 — Eliminar el endpoint AJAX

`routes/admin/geo.php` y su controlador se eliminan. Los selects de país/estado en formularios (Cliente, Configuración General) consultan `Country`/`State` directo en el controlador que arma la vista (`ClientCatalogService`, etc.) — con un solo país real, no hace falta un endpoint de búsqueda dinámica.

**Verificación:** `php artisan migrate:fresh --seed` en una base limpia debe dejar `countries`/`states` con solo RD, sin filas de distrito/barrio. Los formularios de Cliente/Configuración General deben seguir mostrando el selector de estado/provincia con normalidad, ahora sin request AJAX de por medio.

## Fase 9 — Wizard de Completar Instalación (Backoffice) (REQ-09)
**Rama:** `feature/v1.1.0-onboarding-wizard`

### Estrategia

**Distinto del Wizard de Instalación (Fase 8) en quién lo usa y dónde vive.** El de instalación es técnico, se corre una vez al desplegar, casi no lo ve el cliente. Este lo corre **el dueño del negocio**, desde el backoffice (nunca desde el POS — el POS es para el vendedor, no para configurar el sistema), después de que el técnico ya completó el paso 8. Sirve dos propósitos a la vez: enseñarle al dueño cómo se usa el sistema, y dejarle cargados los primeros datos reales (productos, clientes, almacenes) para que no arranque con el sistema vacío.

**Requisito de diseño explícito — reutilización futura:** este wizard tiene que quedar armado de forma que (a) sea fácil agregarle un paso nuevo cuando se sume un módulo nuevo, sin tocar el motor del wizard, y (b) sirva de base directa para el futuro wizard de onboarding del multi-tenant, sin reescribirlo desde cero. Por eso los pasos son **pluggables por módulo**, no una secuencia fija hardcodeada — un negocio en Plan Básico nunca ve el paso de NCF; solo lo ve quien tiene `sales.ncf` activo en su Plan (nunca se le ofrece un wizard de un módulo que no compró).

### 9.1 — Arquitectura de pasos pluggables

```php
// app/Support/Onboarding/OnboardingStepInterface.php

interface OnboardingStepInterface
{
    public function key(): string;                 // 'products', 'clients', 'ncf', ...
    public function title(): string;
    public function requiredModule(): ?string;      // null = siempre visible (pasos base)
    public function isOptional(): bool;              // ej. correlativos: true
    public function livewireComponent(): string;     // clase del paso, cada uno su propio componente
}
```

```php
// app/Support/Onboarding/OnboardingStepRegistry.php

class OnboardingStepRegistry
{
    /** @var OnboardingStepInterface[] */
    protected static array $steps = [
        \App\Support\Onboarding\Steps\ProductsStep::class,
        \App\Support\Onboarding\Steps\ClientsStep::class,
        \App\Support\Onboarding\Steps\WarehousesStep::class,
        \App\Support\Onboarding\Steps\DocumentNumberingStep::class, // opcional
        \App\Support\Onboarding\Steps\NcfStep::class,                // requiere sales.ncf
    ];

    public static function visibleSteps(): array
    {
        return collect(static::$steps)
            ->map(fn (string $class) => app($class))
            ->filter(fn (OnboardingStepInterface $step) =>
                $step->requiredModule() === null || module_enabled($step->requiredModule())
            )
            ->values()
            ->all();
    }
}
```

```php
// app/Support/Onboarding/Steps/NcfStep.php — ejemplo de paso dependiente de módulo

class NcfStep implements OnboardingStepInterface
{
    public function key(): string { return 'ncf'; }
    public function title(): string { return 'Comprobantes Fiscales (NCF)'; }
    public function requiredModule(): ?string { return 'sales.ncf'; }
    public function isOptional(): bool { return false; }
    public function livewireComponent(): string { return \App\Livewire\Install\Steps\NcfSetup::class; }
}
```

Agregar un módulo nuevo al wizard en el futuro (ej. cuando exista Compras) es: crear la clase del paso, agregarla al arreglo del registry, listo — el motor del wizard (`OnboardingWizard.php`, el componente contenedor) nunca cambia, solo itera `OnboardingStepRegistry::visibleSteps()`.

### 9.2 — Contenedor del wizard

```php
// app/Livewire/Install/OnboardingWizard.php

class OnboardingWizard extends Component
{
    public int $currentIndex = 0;

    public function steps(): array
    {
        return OnboardingStepRegistry::visibleSteps();
    }

    public function skip(): void
    {
        abort_unless($this->steps()[$this->currentIndex]->isOptional(), 403);
        $this->advance();
    }

    public function advance(): void
    {
        $this->currentIndex++;

        if ($this->currentIndex >= count($this->steps())) {
            $this->redirect(route('dashboard'), navigate: true);
        }
    }
}
```

## Notas de Implementación

- **Orden de fases no es arbitrario:** 1 (rutas) antes que todo lo que toca middleware de rutas (2, 3, 4, 10), para no reorganizar archivos dos veces. 2 antes que 3 (no se puede gatear Contabilidad de forma segura mientras siga hardcodeada). 3 antes que 4 (NCF necesita el registro genérico ya funcionando). 4 antes que 5 (el seeder de planes referencia `module_key`s que deben existir, incluido `sales.ncf`). 5 antes que 8 (el wizard necesita planes reales). 8 antes que 9 (no tiene sentido cargar datos de negocio sin que la empresa/plan ya estén configurados). 6 y 7 pueden hacerse en paralelo a 2-5, no dependen de ellas.
- **`Plan::assignTo()` es una copia, no una suscripción activa.** No hay lógica de "sincronizar cuando el plan cambia" en esta versión — es trabajo explícito de la futura fase de suscripciones/multi-tenant.
- **El registro de módulos no reemplaza `PosTerminal::getSetting()`.** Son dos sistemas de configuración con propósitos distintos: ajustes de una terminal específica vs. disponibilidad de funcionalidad a nivel de instalación completa.
- **CxC (con su abono), CxP operativa y Cotizaciones nunca deben quedar detrás de `module:accounting.advanced`** (ni de ningún otro flag), en ningún punto de las Fases 2, 3, 8 o 9 — es la regla que más fácil se rompe por accidente si alguien copia el patrón de Contabilidad sin leer esta nota primero. El caso concreto ya confirmado en código: `PaymentService::createPayment()` hoy exige `JournalEntry` para poder abonar (REQ-02.8) — ese acoplamiento es el que hay que cortar, no una hipótesis.
- **El Wizard de Completar Instalación (Fase 9) nunca vive bajo `routes/admin/sales.php` ni se referencia desde el POS** — es exclusivamente backoffice. Si en el futuro se quiere dar un "modo ayuda" dentro del POS, es una feature distinta, no una reutilización de este wizard.
- **`GeoDataSeeder` (Fase 6) asume un dump de solo `INSERT`/`CREATE` simples.** Si en algún momento el dump de RD necesitara procedimientos almacenados o `DELIMITER`, `DB::unprepared()` dejaría de ser suficiente y habría que reconsiderar el enfoque — no es el caso hoy.
- **Seeders `core` deben ser idempotentes** (`updateOrCreate`/`firstOrCreate`), porque el Wizard de Instalación (Fase 8) los ejecuta como parte de `complete()`, potencialmente sobre una base con las tablas ya migradas.
